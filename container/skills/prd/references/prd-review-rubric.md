# PRD 质量打分标准 V1.0（rubric）

> 由 prd-review / version-prd-review 通过 Read 本文件（与其它 prd 参考同目录）消费。原内联于 prd-review/SKILL.md 附录 A-E，抽出为公共参考单一存放。

## 附录 A：V1.0 章节权重 + 豁免逃生口

### 评分原则

- **证据导向**：每个扣分点须引用 PRD 原文或章节位置，不主观臆断。
- **按需参与评审**：先按需求事实和附录 A 规则判断章节是否参与评审；未参与评审的章节直接给满分。
- **Profile 切换**：C 端与后端/中后台用不同权重，评审前先定 Profile。
- **PRD 边界**：PRD 只对功能的输入/输出/业务规则负责；技术实现路径属于技术设计职责，缺失不得扣分。
- **技术声明核查定级上限**：通过代码搜索发现的 gap（非 PRD 主动做虚假声明），最高定级 **P2**。例外：PRD 主动声称「无需开发 / 直接复用」而代码核查显示不存在时，可定 P0/P1。

### 章节权重（两 Profile 对照）

| 章节 | C端 | 后端 | 打分要点速查 |
|---|---:|---:|---|
| 0. 文档元信息 | 5 | 5 | 评估角色信息、版本记录、文档元信息是否完整 |
| 一、需求背景 | 15 | 15 | 现状(6)+用研(5)+竞品(4) |
| 二、需求价值 | 20 | 20 | 定性(8)+定量(12)；写数字+性质即达定量 |
| 三、需求概述 | 3 | 5 | 评估模块关系、范围概览、上下游理解成本 |
| 四、名词解释 | 5 | 7 | 评估关键概念、术语口径、歧义消除是否清楚 |
| 五、需求范围 | 5 | 7 | 评估模块/改动点/负责人/本期不做边界是否清楚 |
| 六、功能详细说明 | 22 | 28 | 6.1流程图(10)+6.2功能说明(8)+6.3历史数据(4) |
| 七、埋点与数据评估 | 15 | 3 | 评估埋点设计、指标口径、效果验证与上线评估 |
| 八、非功能需求 | 5 | 5 | 评估营销/法务/性能/商务/安全等非功能要求是否清楚 |
| 九、项目规划 | 5 | 5 | 评估排期、里程碑、上线计划、协作依赖是否清楚 |
| 十、AI/Cursor 建议 | +0~5 | +0~5 | 加分项，总分不超100 |

### 各章豁免/按需规则

以下规则用于判断章节是否参与评审。未参与评审的章节直接按满分处理，不记录 P 级问题。

- **用户调研(1.2)**：后端功能、纯配置改造、内部流程优化通常不参与评审；涉及用户行为、用户反馈、体验验证时参与评审
- **竞品分析(1.3)**：探索新方向、强体验差异、商业模式对比时参与评审；普通内部改造通常不参与评审
- **需求概述(三)**：模块少、链路短、上下游关系简单时通常不参与评审；模块多、链路复杂、依赖多时参与评审
- **名词解释(四)**：出现新概念、一词多义、跨团队口径差异时参与评审；无新增概念时通常不参与评审
- **历史数据(6.3)**：涉及存量迁移、兼容、回填、清理、展示影响时参与评审；不涉及历史数据影响时通常不参与评审
- **埋点(七)**：C端增长、转化、运营、效果评估类需求通常参与评审；后端需求默认不参与评审，除非明确依赖数据评估、运营监控或效果验证
- **非功能(八)**：涉及营销、法务、性能、商务、安全、审计等要求时参与评审；未触发这些要求时通常不参与评审
- **项目规划(九)**：涉及跨团队排期、里程碑、联调窗口、上线节奏时参与评审；小项目、短周期、单团队改动通常不参与评审

## 附录 B：横切质量原则（总分层面 ±修正）

横切评价评估跨章节的整体质量，不替代 P0/P1/P2 扣分，也不写入单章得分。先按各章 P 级问题算出章节分，再把横切评价净修正作为总分层面的统一修正项。

| 维度 | 意图调整范围 | 判据 |
|---|---:|---|
| 逻辑闭环 | ±2 | 背景→价值→范围→功能→数据评估 能否反向追溯 |
| 可验收性 | ±2 | 能否给出 Given-When-Then 或可执行检查清单 |
| 一致性 | ±2 | 口径/术语/状态名/模块名前后一致 |
| 可读性 | ±1 | 目录/编号/高亮/截图标注便于评审 |

各维度在允许范围内按实际质量判断给值：`0` = 正常/无明显问题，正值 = 明显亮点，负值 = 明显缺陷。

## 附录 C：最终得分计算 + 一票否决

### 扣分规则

| 严重性 | 每条扣分 |
|---|---:|
| P0 | −8 |
| P1 | −3 |
| P2 | −1 |

章节分公式：

```text
章节分 = max(0, 章节满分 − 该章P0条数×8 − 该章P1条数×3 − 该章P2条数×1)
```

汇总公式：

```text
总分 = min(100, max(0, Σ章节分 + 横切评价净修正 + AI/Cursor 建议加分))
```

说明：

- 各章仍按 Profile 章节权重计分，章节满分合计为 100。
- 某章扣分超过该章满分时，该章记 0 分，不出现负分。
- 逐章得分表中的章节行只展示 P 级问题扣分后的章节结果，不混入横切评价和 AI/Cursor 建议。
- 横切评价净修正为所有横切维度的代数和，作为总分统一加减。
- AI/Cursor 建议加分为 0–5 分，总分最高不超过 100。

### 等级线

| 等级 | 分数段 | 结论 |
|---|---:|---|
| A | ≥90 | 通过 |
| B | 80–89 | 通过 |
| C | 65–79 | 补全复评 |
| D | <65 | 退回 |

### 一票否决（5 条）

触发一票否决 → 总分封顶 64，并在顶部汇总表「一票否决」中列明条目。

1. 缺业务目标或无法论证
2. 核心功能与背景/价值脱节
3. 涉及历史数据但无处理方案
4. 涉及资损/合规/法务但未评估
5. 范围严重失控：一期塞多期且无分期说明

## 附录 D：问题严重性定级（P0/P1/P2）

### 总体判定原则

| 级别 | 判定口径 | 每条扣分 |
|---|---|---:|
| **P0** | 研发无法在合理推断范围内确定正确实现，或继续研发会产生严重业务、数据、资损、合规风险 | −8 |
| **P1** | 研发能推进主流程，但存在 2+ 等价实现、关键口径待确认，或实现后可能出现明显体验/业务偏差 | −3 |
| **P2** | 研发可合理实现，问题主要影响表达清晰度、评审效率、局部边界或后续协作成本 | −1 |

### P0：必须产品补齐，否则不建议进研发评审

出现以下任一情况，记 P0：

- **业务目标缺失或无法论证**：没有业务目标、目标与问题无关，或完全无法判断为什么要做。
- **核心功能与背景/价值脱节**：方案解决的不是背景里提出的问题，或价值无法支撑核心功能。
- **核心流程不可实现**：关键触发条件、处理逻辑、输出结果缺失，研发无法确定唯一实现路径。
- **复杂核心链路缺流程图**：涉及多角色、多状态、多系统或长链路流转，但没有流程图/泳道图/时序图，文字也不足以还原唯一路径。
- **核心交互无法还原**：C端或中后台核心页面缺交互图、原型、截图或页面状态说明，研发无法确定页面结构、操作入口和结果反馈。
- **关键状态机缺失**：存在多状态对象，但状态定义、流转条件、终态或回退路径缺失，导致无法实现。
- **关键权限规则缺失**：不同角色/组织/账号权限会影响核心功能，但 PRD 未定义差异。
- **关键数据定义缺失**：核心字段、枚举、合法取值、计算口径缺失，导致前后端或上下游无法对齐。
- **强下游联动缺失接口口径**：依赖下游系统/外部平台/跨团队链路，但输入输出、责任边界或失败处理缺失。
- **涉及历史数据但无处理方案**：影响存量迁移、兼容、回填、清理或展示结果，但没有处理方式。
- **涉及资损/合规/法务但未评估**：支付、退款、权益、合同、隐私、审计、监管等风险未说明。
- **范围严重失控**：一期塞入多期能力，且没有分期、优先级或本期不做边界。
- **主动声明可复用但核查不成立**：PRD 声称「无需开发 / 直接复用 / 零改动」，代码或现有能力核查显示不存在。

### P1：需要产品确认后才能稳妥研发

出现以下情况，通常记 P1：

- **核心分支缺失**：主流程清楚，但异常、失败、取消、撤回、重试、超时等关键分支缺失。
- **流程图缺关键分支**：有主流程图，但缺少异常、回退、权限差异、失败态、跨端/跨系统分支，导致实现存在明显分歧。
- **交互图缺关键状态**：有页面或原型，但缺加载、空态、错误态、禁用态、成功态、二次确认等关键状态。
- **图文存在关键冲突**：流程图/交互图与文字说明在核心规则、操作顺序、状态结果上不一致，需要产品确认。
- **验收标准不完整**：有目标方向，但缺少可检查的上线判据、目标值、口径或验收清单。
- **范围边界不清**：本期做什么大体清楚，但本期不做、灰度范围、适用对象或排除场景不清。
- **文案或用户可见结果待定**：涉及用户可见状态、提示、按钮、通知、结果页，但文案或展示规则未定。
- **权限差异可推断但需确认**：研发能猜到默认权限，但不同角色差异会影响体验或业务结果。
- **数据口径有多种合理解释**：指标、金额、数量、时间窗口、排序、优先级存在多种合理算法。
- **历史数据方案不完整**：已说明会处理存量，但缺影响范围、灰度/回滚、验证方式中的关键项。
- **埋点或评估口径影响验收**：C端需求需要效果评估，但事件、漏斗、指标口径或成功标准缺关键项。
- **项目依赖不清**：依赖跨团队、配置、审核、资源位、外部接口，但责任方或时间点不清。
- **技术声明未能核查**：PRD 主动声称复用现有能力，但当前无权限核查；标注为未核查风险。

### P2：可以研发，但建议补清楚

出现以下情况，通常记 P2：

- **局部描述含糊**：出现「等」「类似」「酌情」「按需」等词，但不影响研发确定主方案。
- **编号、术语或命名轻微不一致**：影响阅读效率，但不影响业务规则判断。
- **截图或示例缺少标注**：研发能结合上下文理解，但评审时需要追问局部细节。
- **流程图标注不完整**：节点、箭头、判断条件、角色归属有局部缺漏，但主流程仍可推断。
- **交互图局部不清**：按钮、字段、提示、排序、默认值等局部细节未标清，但不影响核心实现。
- **图文轻微不一致**：图和文字在命名、编号或非核心展示细节上不一致，研发可合理统一。
- **非核心异常缺失**：缺少低频、边缘、可用通用组件兜底的异常说明。
- **非核心字段说明不足**：字段不影响核心流程，研发可按惯例实现。
- **项目规划略粗**：小项目或单团队改动中，排期/负责人略简，但不影响研发启动。
- **埋点补充项不完整**：已有核心评估方式，仅缺辅助字段或非关键事件。
- **表达结构可优化**：信息分散、重复、顺序不佳，但内容可被合理拼合。

### 历史数据处理专项规则

- 由模型根据需求事实判断是否涉及存量数据迁移、兼容、回填、清理或影响。
- 不涉及历史数据处理 → 直接给满分，不要求 PRD 标注「无历史数据影响」。
- 涉及历史数据处理 → 满分需：处理方式+影响范围+灰度/回滚+验证方法。
- 涉及但未写 → 0分，触发一票否决。

## 附录 E：PRD vs 研发责任边界

### 研发自行决策（不报为 PRD 缺失）

技术方案选择、错误码命名、接口协议细节、异常兜底 UI（有默认组件时）、性能优化、内部查询链路。

### 必须在 PRD 中明确

用户可见状态和文案、业务规则触发条件和分支结果、数据定义和合法取值、权限差异带来的功能差异。

> **判断口诀**：需要研发做业务决策（what to do）→ PRD 应定义；只是怎么实现（how to do）→ 技术路径，不报缺失。
