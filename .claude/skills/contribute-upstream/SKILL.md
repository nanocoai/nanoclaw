# Contribute upstream

Turn a fork's local customizations into generic upstream contributions without losing local
control and without leaking anything internal. Every local edit inside an upstream file is a
future merge conflict; every accepted seam or skill removes one. Four modes. Default is `map`.

| Mode | Trigger | Result |
|------|---------|--------|
| `map` | "map our features", no argument | inventory, classified ledger rows, one decision question per undecided feature |
| `contribute <slug>` | a feature with decision `contribute` | worktree, generic implementation, scrub, Gate 2, push + PR |
| `reconcile` | after `/update-nanoclaw` completes | local code moved onto merged seams, divergences retired |
| `status` | "contribution status", "check the PRs" | status report with state + next action per feature |

Run `reconcile` after every `/update-nanoclaw`: that is when an accepted contribution arrives in
the fork and the local copy can shrink to an override.

## Configuration

Resolve these once per session, before the first step that needs them. Scripts take them as flags.

| Setting | Default | How to resolve / override |
|---------|---------|---------------------------|
| Fork owner (GitHub login) | `gh api user --jq .login` | `pr-status.ts --owner <login>` or env `CONTRIB_FORK_OWNER` |
| Contribution remote | `contrib` | a public GitHub fork of `nanocoai/nanoclaw`; setup in `references/contribution-routes.md` |
| Upstream ref | `upstream/main` | `--upstream-ref <remote>/<branch>` on `inventory.ts` and `pr-status.ts` |
| Ledger | `.nanoclaw-contrib/ledger.md` | `--ledger <path>` |
| Status report | `.nanoclaw-contrib/status.md` | `pr-status.ts --status-file <path>` |
| Scrub denylist | `.nanoclaw-contrib/scrub-denylist.txt` | `scrub-check.ts --denylist <path>` |
| Divergences file (optional) | `.nanoclaw-contrib/divergences.md` | `inventory.ts --divergences <path>`; skipped when absent |
| Extra inventory excludes | `groups/`, `data/`, `logs/`, `.nanoclaw-contrib/` | `inventory.ts --exclude <prefix>` (repeatable) |

The divergences file, when a fork keeps one, lists deliberate edits inside upstream files as
level-two headings: `## D<n> — <title>`.

## Files

- **Ledger**: source of truth for every decision and PR. Never re-ask a feature whose decision is
  `contribute` or `keep-local`. Create it on first `map` with this header row:

  ```markdown
  | # | Slug | Feature | Route | Decision | Decided | Branch | Status |
  |---|---|---|---|---|---|---|---|
  ```

  `#` numbers rows in order of creation. Decision is one of `pending`, `contribute`, `keep-local`,
  `ask-later`. Status holds `in-progress`, `worktree-ready`, `pr-open <url> [<url>...]`, `merged`,
  `closed`, or `adopted`; a feature split into several PRs lists every PR URL in that cell.
- **Denylist**: internal terms for the scrub check (format in `references/scrub-rules.md`).
  Create it before the first contribution and seed it with the fork's name, the local code folder
  name, the operator's work handle and work email domain, and employer or product names.
- **Status report**: generated by `status`. Never edit by hand.
- `scripts/inventory.ts`, `scripts/scrub-check.ts`, `scripts/pr-status.ts`: mechanical helpers,
  run with `pnpm exec tsx .claude/skills/contribute-upstream/scripts/<name>.ts`.
- `references/seam-patterns.md`, `references/contribution-routes.md`, `references/scrub-rules.md`:
  read each once, when the step below that needs it starts.

## Hard rules

1. **Two gates per feature, both through `AskUserQuestion`, never skipped, never batched into a
   single yes for several features.** Gate 1 = may this feature be contributed at all. Gate 2 =
   may this exact scrubbed diff and PR body be pushed and opened. No worktree before Gate 1, no
   `git push` / `gh pr create` / `gh issue create` before Gate 2. A generic "autonomous" or
   "unattended" request does not waive either gate. Only an explicit operator instruction to
   open the PRs (e.g. "create all PRs") counts as standing Gate 2 approval, for that session
   only; record it in the ledger header with the date, and still require a clean scrub and your
   own read of the full diff before each push.
2. **Persist every Gate 1 answer immediately** in the ledger (see Map step 5). That is what
   prevents re-asking in any future session.
3. **Internal systems of your employer or organization are never contributed.** Features that
   integrate them are `local-only` without asking. See the hard excludes in
   `references/scrub-rules.md`.
4. **Scrub gate is blocking.** `scrub-check.ts` must exit 0 on the full branch and the PR body.
5. **Never edit upstream-owned skills** (`update-nanoclaw`, `add-*`) to integrate this one. That
   creates the merge conflicts this skill exists to remove.
6. **Everything goes out under the fork owner's personal identity**: personal git email on every
   commit, the personal `gh` account for push, PR and issue calls, never a work account. The scrub
   check enforces it with `--allow-identity`. Details in `references/contribution-routes.md`.
7. **Push contribution branches only to the contribution remote.** PRs target `nanocoai/nanoclaw`
   `main` (or a registry branch, see Contribute step 1). Never push to `upstream`, never push a
   contribution branch to a private `origin`. Stage only files the task touched.

## Mode: map

1. **Refresh upstream and run the inventory.**

   ```bash
   git fetch upstream --prune
   pnpm exec tsx .claude/skills/contribute-upstream/scripts/inventory.ts
   ```

   It lists divergences (when the divergences file exists), local-only files by area (files owned
   by installed skills filtered out using the `channels`/`providers` registry branches and gateway
   `payload/` directories), upstream files edited ranked by churn, and existing ledger decisions.

2. **Group files into features.** One feature = one user-visible capability or one decision
   changed in upstream code. Use the divergence entries, the fork's own notes, and commit history
   (`git log --follow <path>`) as the grouping source. Give each a stable kebab-case slug. Reuse
   the ledger's slug when the feature already has a row.

3. **Classify each feature** (read `references/contribution-routes.md` and
   `references/seam-patterns.md` now):
   - Route: `bugfix` | `seam` | `skill` | `docs` | `local-only`.
   - For `seam`: pattern P1–P5, the interface name, which upstream edits it removes.
   - For `skill`: skill type and name (`/add-<x>`), what stays local as policy.
   - Upstream duplicate check: `gh pr list` / `gh issue list` against `nanocoai/nanoclaw`.
   - Apply rule 3: internal integrations become `local-only` with reason `internal`.

4. **Write the ledger rows** for new features with decision `pending`, numbering them after the
   last `#`. Do not change rows that already have a decision other than `pending` or `ask-later`.

5. **Gate 1 — ask per feature.** For each row with decision `pending` or `ask-later` and a route
   other than `local-only`, call `AskUserQuestion` (up to 4 features per call, one question each).
   Question text: the feature in one line, route + seam/skill plan in one line, what would be
   public. Options:
   - `Contribute` — build it in a worktree, then ask again before any push.
   - `Keep local` — never ask again.
   - `Ask later` — re-ask on the next `map` run.

   After each answer, update the ledger row: decision and today's date (`YYYY-MM-DD`). If the
   agent keeps a project memory, add one line there pointing at the ledger as the authoritative
   record of contribution decisions.

   Features with decision `contribute` go to `contribute <slug>`, one at a time.

## Mode: contribute `<slug>`

Precondition: ledger decision is `contribute`. If not, stop and run Gate 1 for it.

1. **Worktree** off clean upstream, as in `references/contribution-routes.md`:
   `git worktree add ../nanoclaw-contrib/<slug> -b contrib/<slug> upstream/main`.
   Base on `upstream/channels` or `upstream/providers` instead when the change targets a
   channel or provider adapter (those live on registry branches). When the feature depends on
   another open contribution, branch from that feature's `contrib/<dep>` branch so the PR includes
   both; say "Depends on #<n>" in the PR body and rebase onto the base once the dependency merges.
   Skip creation if the ledger already says `worktree-ready`. Set status `in-progress`.
2. **Implement the generic base** per the route. For a seam: interface, default that reproduces
   current upstream behavior exactly, registration test. For a skill: follow
   `docs/skill-guidelines.md` and CONTRIBUTING (SKILL.md under 500 lines, tests, REMOVE.md when
   apply leaves anything behind). Neutral names only.
3. **Verify** with upstream's full suite inside the worktree (commands in the routes reference).
4. **Scrub** (read `references/scrub-rules.md`): write the PR body from
   `.github/PULL_REQUEST_TEMPLATE.md` to a file outside the worktree, run
   `scrub-check.ts --allow-identity "$(git config user.email)" --diff upstream/main <body-file>`
   with the denylist, fix until clean, then read the whole diff once more by eye.
5. **Gate 2 — ask.** Show `git diff upstream/main --stat HEAD`, `git log upstream/main..HEAD
   --oneline`, the scrub result, and the PR title + body. `AskUserQuestion` options:
   `Push and open PR` | `Revise first` | `Abandon (keep local)`.
   - Push: `git push -u <contrib-remote> contrib/<slug>`, `gh pr create --repo nanocoai/nanoclaw
     ...`, ledger status `pr-open <url>`.
   - Revise: apply the requested changes, repeat steps 3–5.
   - Abandon: ledger decision `keep-local`, leave the worktree for the operator to remove
     (`git worktree remove` needs their request).
6. **Local side, in the main checkout.** Prepare the override on the local branch only after the
   PR merges (see `reconcile`). Until then, the existing local implementation stays as is.

## Mode: reconcile (after `/update-nanoclaw`)

Run after an update completes, and whenever `status` shows a merged PR.

1. For each ledger row whose status is `pr-open`: `gh pr view <url> --json state,mergedAt` for
   every URL in the cell. Update to `merged` once all of them merged, or `closed` if rejected.
2. For each newly `merged` row whose merge commit is now in `HEAD`
   (`git merge-base --is-ancestor <commit> HEAD`):
   - Move the local implementation onto the seam: the local override registers through the new
     upstream interface; delete the local edits inside upstream files the seam replaced.
   - When the fork keeps a divergences file, delete or shrink the matching `D<n>` entry.
   - Run the repo's verification (typecheck, lint, tests), commit, and restart the service.
   - Ledger status `adopted`.
3. For `closed` (rejected) rows: record the maintainer's reason, set decision `keep-local`. Do not
   re-propose unless the operator asks.

## Mode: status

```bash
pnpm exec tsx .claude/skills/contribute-upstream/scripts/pr-status.ts
```

Writes the status report: one row per PR (a feature with several PRs gets one numbered row each)
with state, a link to the PR, detail and the next action. For PRs it reads `gh pr view`: open /
draft / merged / closed, review decision, comments and reviews from others since the last push,
merge state (behind, blocked, unstable) and conflicts. For unpushed branches it reports commits
ahead/behind the base and conflicts via `git merge-tree`. Read-only except that file.

Then act on it, one feature at a time: conflicts or requested changes → `contribute <slug>`
revise loop (Gate 2 again before any push); new comments → read them with `gh pr view <url>
--comments` and draft replies for the operator (posting a comment is outward-facing — ask
first); merged → `reconcile`. To iterate on a schedule, run `/loop 1h /contribute-upstream
status`.

## Troubleshooting

- `inventory.ts` says the upstream ref is missing: `git fetch upstream --prune`. Add the remote
  if absent: `git remote add upstream https://github.com/nanocoai/nanoclaw.git`.
- Push fails with `Repository not found`: the active `gh` account cannot see the contribution
  remote. `gh auth switch --user <fork-owner>`, retry.
- `pr-status.ts` warns the fork owner is unknown: `gh` is not logged in, or pass `--owner`.
  Without it, the owner's own comments count as new feedback.
- Scrub finding is a false positive (e.g. an upstream example address): reword the text. Do not
  add allowlist exceptions for the finding's sake.
- Scrub warns the denylist is missing or empty: create it (see Files) before continuing.
- Worktree install fails on `minimumReleaseAge`: the branch must use upstream's lockfile as is.
  Never add `minimumReleaseAgeExclude` entries in a contribution.
