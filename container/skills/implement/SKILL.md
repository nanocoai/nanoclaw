# 编码实现工作流

kickoff 管"想清楚"，implement 管"动手做"，wrapup 管"收尾沉淀"。

## 核心纪律

1. **不跳步**。每一步有明确的完成标准（Gate），不满足不能进入下一步
2. **不让大杰当测试员**。自己写、自己测、自己审，验证通过才汇报
3. **不自行合并**。提 PR 后必须等用户确认

## 日志纪律

每个步骤完成后输出结构化日志：

```
📋 [步骤名] 状态=✅/❌
  - 产出: xxx
  - 耗时: N 分钟
  - 备注: xxx
```

---

## Step 0: 加载上下文

1. **检查 OpenSpec**：当前项目是否有相关 OpenSpec change？
   - 有 → 读取 design.md 作为实现蓝图
   - 没有 → 从对话上下文提取实现需求，列出要做的事项清单
2. **检查 worktree**：是否已在 worktree 中？
   - 是 → 继续
   - 不是 → 用 `EnterWorktree` 开一个（分支名 `feat/<name>` 或 `fix/<name>`）
3. **列出实现清单**：把要做的事拆成具体的文件级改动列表
4. **确认验收标准**：什么状态算"做完了"

**Gate**: 有明确的实现清单 + 验收标准 + 在 worktree 中

---

## Step 1: 写代码

按实现清单逐项编码。

**要求**：
- 每完成一个模块，确保**编译/lint 通过**（不能积攒错误到最后）
- 改动要**可增量验证**：改一块确认一块，不要一次改 20 个文件然后祈祷
- 如果 OpenSpec 的 design 有明确的函数签名/接口设计，严格遵守
- 记录实现过程中的**关键决策**（为什么这么写而不是那么写），wrapup 时要用
- **日志能记应记尽记**：
  - 关键函数入口/出口打 info 日志（含关键参数和结果）
  - 分支决策点打 debug 日志（走了哪个分支、为什么）
  - 外部调用（HTTP/DB/文件 I/O）打 info 日志（含耗时、状态码）
  - 异常/错误必须打 error 日志（含完整上下文，不能只打 `catch(e) log(e)`）
  - 用结构化日志格式（如 `logger.info({ key: value }, 'message')`），不要拼字符串

**禁止**：
- ⛔ 不写测试（这是 Step 2 的事）
- ⛔ 不做 code review（这是 Step 3 的事）
- ⛔ 不提 PR（这是 Step 6 的事）

**Gate**: 所有清单项已实现 + 编译通过 + 无 lint error

```
📋 [写代码] 状态=✅
  - 改了: file1.py (新增 200 行), file2.py (修改 50 行), ...
  - 编译: ✅ 通过
  - 决策记录: 1) xxx 2) yyy
```

---

## Step 2: 写测试

针对 Step 1 写的代码编写测试。

**要求**：
- **单元测试**覆盖核心逻辑（纯函数、关键分支）
- **集成测试**覆盖关键路径（API 调用链、数据流）
- **边界 case**：空值、超长、并发、异常输入
- 如果 OpenSpec design.md 有测试计划，按计划写；没有就自己规划
- 测试必须**真的在测业务逻辑**，不是测 mock 本身

**测试分层参考**：
- P0（必须有）：核心功能的 happy path + 最关键的异常路径
- P1（应该有）：边界条件、参数校验、错误处理
- P2（最好有）：性能、并发、极端场景

**禁止**：
- ⛔ 不跑测试（这是 Step 5 的事）
- ⛔ 不写"测试桩"占位（`test_xxx(): pass`）
- ⛔ 不跳过难测的部分（难测 = 说明代码可能需要重构）

**Gate**: 测试文件已创建 + 覆盖 P0 全部 + P1 大部分 + 编译通过

```
📋 [写测试] 状态=✅
  - 测试文件: test_xxx.py, test_yyy.py
  - 用例数: P0=N 个, P1=M 个, P2=K 个
  - 编译: ✅ 通过（测试代码本身无语法错误）
```

---

## Step 3: 审代码（双轨）

代码审查分两轮，先 Codex 机审，再人工子 agent 审。两轮都做，互补盲区。

### 3a. Codex Review（自动化机审）

用 OpenAI Codex 插件对当前改动做自动审查。

**执行方式**：用户说"Codex review"时，调用 codex-plugin-cc 插件：

```bash
cd <项目目录> && env -u HTTP_PROXY -u HTTPS_PROXY -u http_proxy -u https_proxy node ~/.claude/plugins/cache/openai-codex/codex/1.0.4/plugins/codex/scripts/codex-companion.mjs review --json --base <base-branch>
```

`--base` 指定对比分支。Nine 项目用 `--base dev`（不是 main）。其他项目按实际情况填。

⚠️ **必须**用 `env -u HTTP_PROXY -u HTTPS_PROXY -u http_proxy -u https_proxy` 剥掉代理变量！Claude Code 注入的 OneCLI 代理会拦截 Codex 的 WebSocket 连接导致卡死。
⚠️ **禁止**直接跑 `codex` CLI（那是独立终端工具，需要 TTY，会卡住）。必须用上面的 `codex-companion.mjs` 脚本。

**其他命令**（同一脚本路径，替换最后的子命令）：
- `status` — 查看当前 review 任务状态
- `cancel <job-id>` — 取消卡住的任务
- `result <job-id>` — 获取已完成任务的结果
- `adversarial-review --json` — 对抗性评审（更严格）

**超时处理**：如果 review 超过 5 分钟没返回，用 `status` 检查，卡住就 `cancel` 后重跑。

插件会：
1. 收集当前 worktree 的 git diff
2. 发送给 Codex 评审器
3. 返回结构化结果（verdict + findings）

**Codex Review 返回格式**：
```json
{
  "verdict": "approve | needs-attention",
  "findings": [
    {
      "severity": "critical | high | medium | low",
      "title": "问题标题",
      "body": "详细描述",
      "file": "文件路径",
      "line_start": 行号,
      "recommendation": "修复建议"
    }
  ]
}
```

**严重级别映射**：
- `critical` / `high` → 🔴 必须修
- `medium` → 🟡 建议修
- `low` → 🟢 可选优化

**Codex Review 的强项**：
- 时序 bug、并发问题、边界条件遗漏（人工 review 容易忽略的）
- 跨函数的数据流分析
- 与 API 契约不一致的问题

### 3b. 子 Agent Review（补充审查）

用 `Agent` 工具 spawn 一个 code review 子 agent，补充 Codex 可能遗漏的业务逻辑和架构问题。

**子 agent prompt 模板**：

```
你是资深代码审查员。审查以下代码变更，给出具体的问题列表。

## 审查范围
{git diff 输出，或改动文件列表}

## Codex 已发现的问题
{3a 步骤的 findings，避免重复}

## 审查标准（重点补充 Codex 盲区）
1. **业务正确性**：逻辑是否符合需求意图，不只是代码层面对不对
2. **安全性**：有无注入、越权、信息泄露
3. **架构合理性**：职责划分、依赖方向、是否过度设计
4. **性能**：有无 N+1 查询、不必要的循环、内存泄漏
5. **可维护性**：命名清晰、无重复代码

## 输出格式
每个问题：
- 文件:行号
- 严重级别：🔴 必须修 / 🟡 建议修 / 🟢 可选优化
- 问题描述
- 修复建议
```

### 审查结果处理（合并两轮）

1. 🔴 必须修的 → 立刻修，无条件
2. 🟡 建议修的 → 判断合理性，合理就修
3. 🟢 可选的 → 记录，不修（除非顺手）
4. 修完后**重新编译确认通过**

**Gate**: 所有 🔴 问题已修复 + 🟡 已处理（修或给出忽略理由）+ 编译通过

```
📋 [审代码] 状态=✅
  - Codex Review: verdict={approve/needs-attention}, 🔴 x 个, 🟡 y 个, 🟢 z 个
  - Agent Review: 🔴 a 个, 🟡 b 个, 🟢 c 个
  - 已修复: 🔴 x+a 个, 🟡 y1+b1 个
  - 已忽略: 🟡 y2+b2 个（附理由）
  - 编译: ✅ 通过
```

---

## Step 4: 审测试

用 `Agent` 工具 spawn 一个测试审查子 agent。

**子 agent prompt 模板**：

```
你是测试质量审查员。审查以下测试代码，评估测试的有效性和完备性。

## 被测代码
{Step 1 写的代码核心部分}

## 测试代码
{Step 2 写的测试代码}

## 审查标准
1. **覆盖率**：核心逻辑是否都有测试，有无遗漏的分支
2. **有效性**：测试是否真的在验证业务逻辑，而非测 mock
3. **独立性**：测试之间是否互不依赖，可单独运行
4. **可读性**：测试名称是否描述了被测行为
5. **边界覆盖**：空值、极端值、异常路径是否覆盖
6. **脆弱性**：测试是否过于依赖实现细节（改一行代码就要改 10 个测试）

## 输出格式
- 遗漏的测试场景列表
- 每个问题：🔴 必须补 / 🟡 建议补
- 现有测试中需要修改的问题
```

**收到审查结果后**：
1. 🔴 必须补的测试 → 补写
2. 🟡 建议补的 → 判断后决定
3. 修改有问题的现有测试
4. **重新编译确认通过**

**Gate**: 所有 🔴 遗漏已补 + 测试代码编译通过

```
📋 [审测试] 状态=✅
  - 审查发现: 遗漏 🔴 x 个场景, 🟡 y 个场景
  - 已补写: 🔴 x 个, 🟡 y1 个
  - 现有测试修改: z 处
  - 编译: ✅ 通过
```

---

## Step 5: 跑测试

运行全量测试。

**要求**：
- 跑**全部**测试，不是只跑新写的
- 如果项目有 CI 命令（`npm test` / `pytest` / `go test`），用标准命令
- 必须看到**完整的测试输出**，不能只看退出码

**如果测试失败**：
1. 分析失败原因
2. 修复代码或测试（取决于是代码 bug 还是测试写错）
3. 重新跑，**循环直到全绿**
4. 如果循环 3 次以上仍有失败，停下来汇报给用户，说明卡点

**Gate**: 全量测试通过（0 failures）

```
📋 [跑测试] 状态=✅
  - 命令: pytest / npm test / ...
  - 结果: X passed, 0 failed
  - 循环次数: N（首次通过 = 1）
```

---

## Step 5.5: E2E 测试用例设计（条件触发）

改了外部可观测行为（消息收发、卡片、定时任务、API 交互）时触发。纯内部重构不触发。

> 完整 E2E 执行+汇报流程见 `e2e-testing` skill。本步骤只管用例设计和确认。

### 流程

1. 根据本次改动，列出测试用例表发给大杰：

| # | 场景 | 触发方式 | 预期结果 |
|---|------|---------|---------|

2. 大杰确认后执行，逐条验证并汇报结果

### 用例设计原则

- **从用户视角写**：描述用户做了什么、看到什么，不写内部实现细节
- **一个用例验一个行为**：不堆砌，一条看不出对错的就拆
- **必须包含回归项**：改了 A 功能，验 A 的同时也验 A 相邻的 B 没被搞坏
- **预期结果要具体**：不写"正常工作"，写"飞书收到卡片且 footer 包含 💰"

**Gate**: 用例表已发给大杰 + 大杰确认 + 逐条执行通过

```
📋 [E2E 测试] 状态=✅
  - 用例数: N 个
  - 通过: N 个
  - 失败: 0 个
```

---

## Step 6: 提 PR 等待确认

1. 将所有改动提交（commit message 遵循项目规范）
2. 创建 PR（标题简洁，body 包含改动摘要 + 测试结果）
3. 向用户汇报

**汇报格式**：

```
## 实现完成

**PR**: {链接}

**改了什么**：
- {文件级改动摘要，3-5 条}

**测了什么**：
- {测试覆盖摘要}
- 全量测试结果: X passed, 0 failed

**审了什么**：
- 代码审查: 🔴 x 已修, 🟡 y 已修/z 忽略
- 测试审查: 补了 N 个遗漏场景

**E2E**（如有）：
- {N} 个用例全部通过

**等你确认**：说"合"我就 merge，说"改 xxx"我回去改。
```

**禁止**：
- ⛔ 禁止 `--auto` 自动合并
- ⛔ 禁止不等确认就 merge
- ⛔ 禁止在汇报中隐瞒已知问题

**Gate**: PR 已创建 + 汇报已发送 + 等待用户指令

---

## Step 7: 用户确认后操作

- 用户说 "合" / "merge" / "可以" → 执行合并（遵循项目 merge 规范）
- 用户说 "改 xxx" → 回到对应步骤修复，然后从修复点重新走后续流程
- 用户说 "不合了" / "取消" → 标记 PR 为 draft 或 close

---

## 异常处理

| 场景 | 处理方式 |
|------|---------|
| 编译失败修不好 | 停在当前步骤，汇报具体错误，等用户指示 |
| 测试死循环（3次+修不过） | 停下来，列出每次失败的不同原因，等用户判断 |
| 审查意见跟 OpenSpec 矛盾 | 以 OpenSpec 为准，记录矛盾点汇报给用户 |
| 发现需求理解有误 | 立刻停下来跟用户确认，不要带着错误理解继续写 |
| worktree 冲突 | 不要 force，汇报冲突内容让用户决定 |
