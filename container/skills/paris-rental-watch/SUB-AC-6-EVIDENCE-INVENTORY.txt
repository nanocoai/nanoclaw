================================================================================
Pattern definition (what counts as a SUB-AC-*-EVIDENCE.txt artifact)
================================================================================
The convention, fixed by the prior `host-helpers/cf-fetch-server/SUB-AC-*`
files in this repo, is:

  - Filename             : `SUB-AC-<n>[.<m>][-LABEL]-EVIDENCE.txt`,
                           where `<n>` indexes the parent AC and `<m>`
                           the sub-AC inside it (Sub-AC split is allowed
                           when one Seed AC needs more than one auditable
                           action — see AC 3 below).
  - Location             : same directory as the artifact under test
                           (skill folder for skill-side ACs; sidecar
                           folder for host-side ACs).
  - File body must include:
      a) Header (Seed name + AC number + AC text verbatim).
      b) Pre-state — what the system looked like BEFORE the AC's edits
         (logs, file listings, grep results, launchctl list, etc.).
      c) Edits / actions applied — the concrete delta.
      d) Post-state — the same probes re-run after the change, with the
         differences called out.
      e) Verdict block — `[PASS]/[FAIL]` for each Seed sub-condition
         derived from the AC text and any evaluation principle it maps
         to.
      f) Notes for downstream ACs (handoffs, deferred work, sibling
         dependencies).

  - Plain text (.txt), no Markdown rendering required (these files are
    archived alongside source and read raw by reviewers / future ACs);
    fenced sections are 80-column ASCII rule lines.

Open warnings carried forward from the Coordinator Review (not blocking AC 6)
================================================================================
The Coordinator Review at level 3 flagged three warnings that survive AC 5
and remain in scope for any subsequent AC, but do NOT invalidate the
evidence corpus this AC inventories:

  W1. SKILL.md line 235 still carries the comment
        # Conservative pre-filter — host fetch.py 포팅.
      A literal "host fetch.py" reference. This is documentation drift,
      not behaviour: the comment annotates a defensive pre-filter that
      runs entirely inside the container. AC 3.4's grep ruleset
      (paris-pap|staging-file|com.nanoclaw.paris) did not catch the
      bare phrase "host fetch.py". Recommend: drop the "— host fetch.py
      포팅" clause and re-state as "host-side fetcher 없음" (matches the
      Sub-AC-3.4 negation convention). This SUB-AC-6 file does NOT
      attempt that edit — AC 6 is a meta-AC and should not silently
      mutate a sibling AC's surface.

  W2. `from pap_failure_log import …` is duplicated in SKILL.md Section C
      (line 154) and Section 6 (line 436). Harmless today (Section C
      installs SKILL_DIR onto sys.path before the Section-6 reload), but
      brittle if a future AC ever extracts Section 6 into its own
      process. Recommend: hoist the import to a single top-of-skill
      Python preamble. AC 6 leaves the duplication in place and only
      records the warning so a future maintainer sees the rationale.

  W3. The seven SUB-AC-*-EVIDENCE.txt files (this corpus) sit next to
      runtime code under container/skills/paris-rental-watch/ and
      container/skills/web-fetch/. They are point-in-time snapshots,
      not container runtime. If a future AC rebuilds the container
      image they will ship inside it. Recommend: a `.dockerignore`
      filter for `**/SUB-AC-*-EVIDENCE.txt` (and `**/VERIFICATION-*-
      EVIDENCE.txt` for cf-fetch-server) before the next image build.
      AC 6 leaves the layout untouched: moving the files now would
      itself break every md5 in this manifest and force a re-audit.

These three items are forwarded as `notes_for_downstream` and do not
gate this AC's PASS.
