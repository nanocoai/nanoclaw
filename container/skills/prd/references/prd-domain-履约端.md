# 履约域 PRD 参考（prd-domain-履约端）

> 履约域特有规则。通用写作规律见 prd-core.md，工序流程见 prd-pipeline.md。

## 域定位

**履约端 vs 交易端**：框架同为 NINE 10 章，样式/格式执行细则同交易端（mermaid 图类型表/示例/安全语法/视觉规范、各章 schema、代码引用边界表见 prd-core.md）。履约端在此之上**额外**给三样：

1. **五/六章「按内容选格式」决策表**——履约六章内容异质度高（规则/算法/状态竞态/跨系统/异常混在一起），不宜像交易端那样"必用 5 列表"套死；用「内容→结构决策表」按内容选。主力表用履约事实标准的**「内容/说明/示例」三列**（126 篇里 54 篇在用）。
2. **履约专属内容清单**（资金保证金闭环 / 质检鉴别 / 跨系统时序 / 存量数据 / 幂等协议 / 配置权限）。
3. **人写习惯纪律**（反 AI 味）。

一句话理念：**格式服从内容复杂度**。内容简单就一句话，复杂到会扯皮才上表/矩阵/图/伪代码。

## 域章节清单

按下表锚定标题避免遗漏（实测头部/版本/存量数据等基础章节常被跳过）。

### A 类 — 必写（标题 + 实质内容）
| 章节 | 内容要求 |
|---|---|
| **头部 · 协作域/负责人表** | 2 列表（schema 见「章节实操：头部与一~五章」）；履约需列全 95交易/95履约/OFC/WMS/质检鉴别各方 |
| **版本变更表** | 4 列表（版本/时间/变更人/内容）|
| **一、需求背景** | 段落 + 真实 case + 数字（不能只写"效率低"）|
| **二、需求价值** | 定性或定量（现状 vs 目标两栏）|
| **五、需求范围** | 见「五章范围写法」（含「本期不做」）|
| **六、功能详细说明** | 6.1 流程图（白板块）+ 功能主体（格式按「内容→结构决策表」）+ **6.4 存量数据处理（履约几乎必写）** |

### B 类 — 按条件必写
| 章节 | 触发条件（机械判断） | 写法 |
|---|---|---|
| 七、埋点 | 涉「前端/移动端」→ 写；**纯后端/内部工具→省**（履约多为后端，默认省）。三分类 `server/=后端 web/=前端 mobile/=移动端`，域/平台见 business-map.md | 标题 + 引导模板（见「条件章节」七） |
| 八、非功能 | 涉资金结算/法务合规/性能容量/灰度 任一 → 写实质（**履约常涉资金→常需写**）；无→省 | 标题 + 引导模板（见「条件章节」八） |

### C 类 — 推荐写（简单需求可省）
| 章节 | 跳过条件 |
|---|---|
| 三、需求概述 | 仅单一功能点、无模块间依赖 |
| 四、名词解释 | 无任何新概念 |
| 6.2 交互原型图 | 纯后端/内部工具（无 UI）|

### D 类 — 按需写
| 章节 | 触发条件 |
|---|---|
| 6.5 状态与资金闭环 | 履约状态联动保证金/跨公司资金结算时 |
| 6.6 跨系统契约与幂等 | 跨得物/多方系统交互时 |
| 6.7 配置化与权限 | 用配置中心动态规则时 |
| 九、项目规划 | 大型项目（多模块/多团队/里程碑）|
| 十、AI 审视 | research 有实质洞察 |

## 内容→结构决策表

从 126 篇人写履约 PRD 反推的「内容类型 → 该用什么格式」。写五/六章对号入座。

| 要表达的内容 | 推荐格式 | 反面（AI 常犯） |
|---|---|---|
| 需求背景 / 问题 / 补充说明 | 平铺段落，穿插真实数字与单号 | 硬塞表格，割裂 |
| 版本变更、协作域责任人 | 表格（固定列） | 写成一段话，找人难 |
| 需求价值 | 现状 vs 目标 两栏对照 / 新旧体验推演 | 只写"提升效率" |
| 多场景准入 / 业务规则枚举 | 表格：场景/条件/结果/**是否和现状不同** | 大段文字罗列规则 |
| 复杂功能（多字段、多分支、需逐条对照） | **「内容/说明/示例」三列表**（履约主力），单元格内可再嵌 bullet | 拆 #### + bullet，丢对照性 |
| 计算/撮合/判定逻辑（算法性） | 结构化文字（小标题 + 多级缩进 bullet）或伪代码（if/return），**规则后紧跟代入真实数字的算例** | 塞进表格挤成一团；只给公式不给算例，评审无法验算 |
| 状态竞态 / 时序准入（某状态下能否触发某动作） | **互斥矩阵表**（状态 × 事件 → 是否允许 + 说明） | 文字"如果…那么"，漏组合 |
| 异常 / 边界场景处理 | 表格：场景/触发条件/处理方式/**终态** | 只写主流程，异常散落 |
| 跨系统交互流程（多方/多状态/有时序） | **白板/mermaid 流程图**（正文配一句业务概括） | 大段文字；或只写"见画板" |
| 字段新增/变更清单 | 列表用「(新增)」前缀原地标；或表（逻辑实体/字段/说明/新增或变更） | 另起"变更前后对照表" |
| 存量/历史数据处理 | 表格：场景/处理方式/SOP（SOP 列箭头串步骤） | 一句"无历史数据影响"糊弄 |
| 灰度上线/回滚 | 表格：阶段/范围/观测时长/通过条件 + 回滚触发列表 | 只写"灰度上线" |
| 具体 case 佐证 | 举例推演：真实单号/编码 + 现网截图 | "示例1/参数A"占位 |
| 重复出现的口径/规则/文案 | 单一真源（一处定义成表），其余位置按名引用，改一处全篇生效 | 多处逐字复制，改漏不同步 |
| 单点小改动 | 一句话 或 一行嵌进列表 | 为小改动画流程图 + 建表 |

> **判断口诀**：这块内容"研发/评审会不会为它扯皮"？会 → 上结构（表/矩阵/图/伪代码）把边界钉死；不会 → 一句话平铺。**篇幅克制是优点**（范例全文常 80 余行，重点极突出）。

## 章节实操：头部与一~五章

### 头部 · 协作域/负责人表（文档最顶部）

| 协作部门 | 负责人 |
|----------|--------|
| 业务 | [对应业务域中文名] |
| PMO | （留空）|
| 产品 | [当前会话用户姓名] |
| 相关文档（MRD/交易/OFC/WMS） | [飞书 URL / 留空] |

⚠️ 反例：别写成段落"由产品 A、设计 B 协作…"——PM 找人困难。履约需求跨方多，责任人表尤其要把 95交易/OFC/WMS 各对接人列全。

版本变更表：见 prd-pipeline.md「版本变更表协议」。

### 一、需求背景
- **产品/数据现状**：沿用用户/飞书原文；**举真实 case + 数字**（"3月9日下发19次、7个仓、唯一码9525…"），别空泛。
- **用户调研**：无素材直接跳过，不编造。
- **竞品分析**：可陈述友商公开同类功能；不编造转化率/MAU。

### 二、需求价值（A 类）
论证"为什么值得做"，**不能只写"提升体验"**。履约优先用**「现状 vs 上线后目标」两栏量化对照**（卡单率9%→0%、效率4h/天→4h/周）；量化不了才补定性。反例：❌"优化流程"。

### 三、需求概述（C 类）
多模块交互依赖时写，单点可跳过。开头先一句话讲清本质（做什么 + 边界，如「把 X 从…改为…；不含…」）再展开，别一上来堆细节让读者自己拼主线。

### 四、名词解释（C 类）
| 名词 | 定义 |
|------|------|
| AQAE | [履约质检成色判定编码体系] |
| 一检/二检 | 仓内两级质检链路 |

原则：与代码实体命名对齐；不写通用技术词（"接口"/"数据库"）。

## 五章范围写法

**格式按改动形态选**（不强制某一种）：
- 改动点清晰可逐条列 → **3 列表**：模块/改动点/负责人。
- 多来源/多场景（融合订单区分貔貅+自营、多仓多批次）→ **「内容/说明/示例」三列**。
- 单点改动 → 一句话平铺。

3 列表 schema + 例：

| 模块 | 改动点 | 负责人 |
|------|--------|--------|
| [业务域 · 后台模块] | [具体改动，如：新增货架校验拦截] | 后端 |
| [业务域 · 服务/接口] | [如：字段透传 OFC] | 后端 |
| 本期范围外 | [明确排除] | — |

✅「履约域 · 批量取回 | 下发前增货架校验拦截 | 后端」← 业务域名 + 改到功能级 + 负责人
❌「优化批量取回 | 不确定」←「优化」太模糊、"不确定"空头
⚠️ 别用仓库名/服务名（PM 看不懂）：
❌「ms-order-reverse · 取回枚举 | 新增 RetrieveType_2」　✅「履约域 · 取回规则 | 新增批次取回类型」

**必含「本期不做」**（≥2 条，防范围蔓延；单独一段或并入"风险接受"表，别与验收混）。履约尤其写清：拆单/部分出库是否按子单处理、存量是否回溯、哪些品类/仓不在本期。

## 6.1 域注

履约 6.1（产品架构图 & 流程图）：**先结构后时序**。

**先静后动（复杂 / 大需求必读）**：先画一张**产品架构图**（静态：有哪些系统 / 模块 / 数据存储 + 谁依赖谁，如 95交易 / 95履约 / OFC / WMS / 数据库），再画流程 / 时序图（动态：谁先告知谁）。架构图回答"有哪些东西、怎么摆"，流程 / 时序图回答"消息怎么流"——复杂需求两者都要。命中任一即需架构图：**新增系统对接** · **改动跨 ≥3 个系统** · **引入新单据 / 新状态机** · **部署拓扑变**。单点小改动不需要。

**何时画（流程 / 时序类）**：多角色/多状态/多系统协作时。履约几乎都涉及多方（95交易→95履约→OFC→WMS，或质检→鉴别→出库）。**履约特别关注"谁先告知谁"**（如"供应链先于交易通知关单"）——时序依赖要在图里体现。简单线性（≤5 节点无分支）可省或降级 Plaintext 箭头链。

图的画法与语法见 prd-core.md 6.1a/6.1b。

## 6.3 功能主体与质量标准

履约主力用 **「内容/说明/示例」三列表**逐个子功能点写（内容/说明/示例；复杂子功能单元格内嵌 bullet）；**每条尽量给真实示例值**（真实单号/库位/仓编码/AQAE code），不用占位符。按「内容→结构决策表」：规则枚举→准入表（含"是否和现状不同"列）/ 算法判定→嵌套 bullet 或伪代码 / 状态竞态→互斥矩阵 / 异常边界→场景四列表 / 跨系统→白板图。

（若是偏 C 端展示型的履约需求，也可用交易端的「域/模块/功能/详细说明/交互图」5 列表。）

**每条功能说明的质量标准（不论用哪种表）**：
- **触发条件 + 处理逻辑 + 返回结果 三段齐全**；
- 边界/异常在同一处描述（"调用 X 失败时降级展示 Y"），不另起；
- 涉状态机：列全部合法状态 + 流转条件（含**禁止流转**，如"已出库后不可取消"），不能只写部分。

⚠️ 反例——别把多模块拆成 `####` + bullet（失去逐条对照性，PM 滚屏难比对）。

## 条件章节

### 6.4 历史 / 存量数据处理（履约几乎必写，别省）
履约上线几乎都要处理仓内存量数据。用**表格**（场景/处理方式/SOP，SOP 列箭头串步骤）写清：成色升级/降级或字段迁移的一次性刷数方案、数据对账 + 客服布防确认、处理原则（常见"只对新入仓增量生效，保留历史现场选择结果"）。**涉存量却不写处理方案 = 一票否决项。**

### 6.5 状态与资金闭环（D 类，涉资金必写）
履约状态变化常**直接联动跨公司资金结算**（寄售单关单 ↔ 卖家保证金退/扣）。涉及时写：**双终态定义**（A=关单受理成功 / B=保证金退还成功）+ A成功B未知的补偿/对账机制；拆单/部分出库/迟到鉴别的资金边界；Oncall 人工补偿 SOP（替代研发刷数）。

### 6.6 跨系统契约与幂等（D 类，跨得物/多方时写）
- 接口契约若未与对方谈妥，显式标 `⚠️ 待对齐 + Owner + 预期时间`，别假装谈妥；
- **幂等键 + 协议版本号**应对对方原因码/契约变更（含"双版本并行窗口 + 在途单据收口"迁移）；
- **不信任边界**：跨系统入参二次校验（如状态不接受倒退）。

### 6.7 配置化与权限（D 类，用配置中心时写）
配置中心动态规则（不发版、<5min 生效）时，写清配置项 + **变更权限矩阵**（产品发起/Lead 审批/开发紧急操作）。

### 七、埋点（B 类）
触发：涉「前端/移动端」→ 写；纯后端/内部工具→省（履约多为后端，默认省）。
**引导模板**：
> 埋点参数涉 NINE 内部规范，建议跟数据团队对齐后补全。常见维度：当前页 id / 模块 / 触发动作 / 上下文参数 / 新增 or 调整。

### 八、非功能（B 类）
触发：涉资金结算/法务合规/性能容量/灰度 任一 → 写实质。
**引导模板**（按发现类型分块）：
> - **资金/资损**：跨公司结算、保证金、对账兜底、补偿 SOP（履约高频）
> - **法务/商务**：合规、外部合作签约状态
> - **性能容量**：批量下发/查询接口 QPS、峰值（如大促）
> - **灰度方案**：分批范围/节奏/回滚条件——用表（阶段/范围/观测时长/通过条件）+ 回滚触发列表；灰度期指标与全量目标**分开统计**（如灰度允许"回滚悬挂单"单列，不与全量后 0 进线混）。

### 九、项目规划（D 类）
大型项目（多模块/多团队/里程碑）用推进表，明确各协作方要做的内容 + 优先级 P0/P1/P2。可用甘特图。小项目跳过。

## 履约专属内容清单

写六章时对照，看漏没漏——相比交易/C端 PRD 高频、且它们基本不出现的内容。按需求命中勾选：

- [ ] **跨系统时序**：95交易 / 95履约(ms-black) / 得物OFC / 得物WMS / 质检鉴别，谁先告知谁
- [ ] **资金/保证金闭环**：履约状态 ↔ 跨公司资金结算、双终态、补偿对账、人工 SOP
- [ ] **质检/鉴别节点**：一检/二检/豁免、鉴别状态×出库时序互斥、AQAE+四级标签成色判定、防伪绑扣/证书/唯一码
- [ ] **仓内作业**：取回/退供出库事件消费、上架、分拣标签、打包状态回传（待打包/打包完成/已出库）、洗护模式（无洗 vs 非无洗）
- [ ] **融合订单**：貔貅+自营来源区分、字段标订单来源
- [ ] **批次/仓维度批量操作**：按「仓+批次号」下发（区别 C 端单订单粒度）
- [ ] **物流回传**：承运商/承运商产品/运单号、自提司机/车牌/联系方式（同批次可多次覆盖）、自提超期转快递
- [ ] **存量历史数据**：刷数 SOP + 对账 + 客服布防（几乎必写）
- [ ] **跨公司契约**：接口契约冻结、幂等键 + 协议版本、双版本迁移窗口、不信任边界二次校验
- [ ] **配置中心动态规则** + 变更权限矩阵
- [ ] **寄存差异**：普通寄存 vs 企业寄存（科目/审批链/对接主体）

## 人写习惯（域项）

1. **格式服从内容复杂度**，不一套到底（本域核心）。
2. **聚焦克制**：全篇围绕核心决策，不为显得完整堆无关模块；单条说明一两句话。
3. **迭代对照**：用「是否和现状不同 ✅/❌」列 或「(新增)」前缀 或「本期改造 vs 已支持[日期]」，把本期变更和沿用分清。
4. **举真实 case**：真实单号/编码/仓号，不用"示例1/参数A"；配现网截图。
5. **现状量化对照**：价值/指标给"现状 + 目标"两栏。
6. **协作缺口显式标待办**：`⚠️ 待与X对齐 · Owner · 预期时间`，不假装谈妥。
7. **没内容就留空/省章**，不为填满硬凑图或表——但"存量数据""跨系统时序"这两处别偷懒省。
