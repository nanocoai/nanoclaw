# E2E 端到端测试

## 铁律

```
测试通过要有证据，测试失败要有根因。
"跑了一遍没问题"不是汇报。
```

---

## 第一阶段：准备

### 1. 查找已有测试用例

**第一步永远是查用例库**，不是直接开跑：

1. 读 `wiki/e2e-test-catalog.md`，按模块找本次改动相关的用例
2. 找到了 → 确认用例是否需要更新（改动可能导致预期结果变化）→ 进入步骤 3
3. **没找到 → 必须先设计用例**（见步骤 2），设计完发出来，然后**直接继续执行**

⚠️ **没有测试用例不允许开始执行。** "直接发几条消息看看"不是 E2E 测试。

### 2. 设计测试用例（无现成用例时）

按 `implement` skill Step 5.5 的标准设计：

| # | 场景 | 级别 | 触发方式 | 预期结果 | 验证方式 |
|---|------|------|---------|---------|---------|
| 1 | {从用户视角描述} | L1/L2/L3 | {具体操作} | {具体可验证结果} | {怎么确认} |

**用例设计原则**（来自 implement skill）：
- **从用户视角写**：描述用户做了什么、看到什么，不写内部实现细节
- **一个用例验一个行为**：不堆砌，一条看不出对错的就拆
- **必须包含回归项**：改了 A，也验 A 相邻的 B 没被搞坏
- **预期结果要具体**：不写"正常工作"，写"飞书收到卡片且 footer 包含 💰"

**流程**: 用例表通过 `send_message` 发出来（让大杰看到），然后**不等确认，直接继续执行后续步骤**。假设设计的用例没问题，保持连贯。

### 3. 确定测试环境

| 平台 | Debug API | 关键参数 |
|------|-----------|---------|
| NanoClaw | `POST http://127.0.0.1:19877/send` | `jid=fs:oc_xxx&text=xxx`，必须 `--noproxy '*'` |
| Nine | `POST http://10.117.5.134/debug/chat` | `wait: false`（**强制**），`X-Debug-Key: nine-debug-test-2026` |

⚠️ Nine 必须 `wait: false`，否则不发飞书消息，大杰看不到。

### 4. 清理旧任务

新轮次启动前**必须**清理：
- NanoClaw：确认单进程运行（`ps aux | grep dist/index.js | grep -v grep`）
- Nine：把 `running`/`interrupted` 超 30 分钟的任务标 `failed`
- 确认无残留 VM / worktree

### 5. 确认部署就绪

- NanoClaw：`npm run build` + 重启 + 验证 dist 包含改动
- Nine：PR 合并到 dev → 等 GitHub Actions 部署完成（~60s）→ `ssh dev "docker ps"` 确认容器在跑

## 第二阶段：执行

### 逐条执行

- 每个用例**独立执行**，不要批量发
- 每个用例执行后：
  1. 等待回复完成
  2. 检查飞书消息是否符合预期
  3. 检查日志无报错
  4. 记录结果：✅ 通过 / ❌ 失败 + 原因

### 日志检查

| 平台 | 命令 | 关键词 |
|------|------|--------|
| NanoClaw | 读 `logs/nanoclaw.log` | `[reply]`、`ERROR`、`WARN` |
| Nine | `ssh dev "docker logs nine-backend --tail=100"` | `AGENT_LOOP`、`tool_calls`、`ERROR` |

### 失败用例处理

用例失败时**不要跳过**，当场定位：
1. 读完整错误日志
2. 确认是代码问题还是环境问题
3. 如果是代码问题 → 加载 `systematic-debugging` skill 走定位流程
4. 修复后**重跑该用例**验证

## 第三阶段：汇报

### 汇报格式（强制）

```
🧪 E2E 测试报告

结论：X/Y 通过 [✅ 全部通过 / ⚠️ 部分失败 / ❌ 全部失败]

通过用例：
  ✅ [用例ID] {描述} — {验证方式}
  ✅ [用例ID] {描述} — {验证方式}

失败用例：（每个失败必须包含以下全部内容）
  ❌ [用例ID] {描述}
     一句话：{什么坏了}（≤20字）
     
     期望 vs 实际：
     ┌─ 期望流程 ─────────────────┐
     │ 用户发消息                    │
     │   → agent 处理                │
     │   → 调用工具 A                │
     │   → 返回结果给用户            │
     └─────────────────────────────┘
     
     ┌─ 实际流程 ─────────────────┐
     │ 用户发消息                    │
     │   → agent 处理                │
     │   → 调用工具 A                │
     │   ✗ 工具超时，无响应          │
     └─────────────────────────────┘
     
     证据：{日志原文 / 截图 / curl 响应}
     根因：{基于证据的判断}
     修复状态：[已修复并重跑通过 / 未修复，原因是 XX]

环境：
  - 平台：NanoClaw / Nine DEV
  - 时间：YYYY-MM-DD HH:MM
  - 相关 commit / PR：{hash 或 PR 链接}
```

### 汇报规则

1. **结论先行** — 第一行就是 X/Y 通过，不要先讲过程
2. **失败必须画流程对比** — 期望 vs 实际的 ASCII 流程图是**强制项**，不画不算完成汇报
3. **证据不能省** — 每个失败用例必须附日志原文或截图，"报错了"不是证据
4. **禁止模糊描述**：
   - ❌ "部分用例不通过" — 哪些？
   - ❌ "日志有报错" — 什么报错？
   - ❌ "涉及 a.ts、b.py、c.go" — 这是废话
   - ❌ "应该没问题了" — 跑了吗？
5. **通过也要有验证方式** — 不是"看起来正常"，是"飞书收到回复 + 日志无 ERROR"
6. **未修复的失败必须说原因** — 为什么没修？是等 PR 还是需要讨论？

## 用例沉淀

执行完 E2E 后，把**新设计的用例**补充到 `wiki/e2e-test-catalog.md`，避免下次重复设计。

> 用例设计的完整流程见上方"第一阶段 → 步骤 2"，或 `implement` skill 的 Step 5.5。

## 常见坑

| 坑 | 表现 | 解决 |
|----|------|------|
| JID 缺 `fs:` 前缀 | FOREIGN KEY 错误 | 跨群 JID 必须带 `fs:` |
| Nine `wait: true` | 飞书没消息 | 改 `wait: false` |
| 跨应用 open_id | "未授权用户" | 检查是否用了正确应用的 open_id |
| 旧任务残留 | heartbeat 报错刷屏 | 先清理再跑 |
| event_id 重复 | 消息被去重拦截 | 每次用新的 event_id |
| `docker compose restart` 不重读 env | 配置不生效 | 用 `docker compose up -d` |
| npm run build 后没重启 | 改了没生效 | build → 重启 → 验证 dist |
