Sub-AC 3 — Structured logging in the wrapper CLI
=================================================

Requirement
-----------
> Add structured logging in the wrapper CLI (always-on attempt trace plus
> --verbose detail) that records each attempt's runtime, the detected CF
> signal, and the fallback decision so verification can confirm the
> sequence from logs.

Decisions
---------
The orchestrator (Sub-AC 2.4) already emits structured JSON log lines to
stderr at INFO level for the always-on attempt trace. Sub-AC 3 closes the
loop by:

  1. Exposing two CLI flags on `web_fetch.py` so an operator can adjust
     the threshold for one call without exporting an env var:

       --verbose / -v   →  WEB_FETCH_LOG_LEVEL=DEBUG   (adds detail)
       --quiet   / -q   →  WEB_FETCH_QUIET=1           (silences trail)

     Precedence: --verbose wins over --quiet (explicit per-call opt-in
     beats the silencer); both flags scrub conflicting ambient env so a
     stale `WEB_FETCH_QUIET=1` doesn't muzzle an explicit --verbose.

  2. Threading the resulting env into `orchestrator.run_fetch(env=...)`
     via `_build_orchestrator_env`. When neither flag is passed the
     ambient env is forwarded unchanged so persistent
     `WEB_FETCH_LOG_LEVEL` exports keep working.

  3. Documenting the verbosity contract in SKILL.md, including the
     mandated three fields (runtime, CF signal, fallback decision) and
     where each one lands on the structured log.

The "always-on attempt trace" was already in place from Sub-AC 2.4 — the
INFO-level events `fetch.start`, `primary.complete`, `fallback.decision`,
`sidecar.start`, `sidecar.complete`, and `fetch.complete` are emitted on
every invocation regardless of flags. Sub-AC 3 simply makes the CLI
expose the verbosity knob and pins the contract under tests.

How verification reads the sequence
-----------------------------------
A single grep over stderr at default verbosity yields the deciding trail:

    web-fetch <url> 2> >(jq -c 'select(.event)') > /tmp/page.json

The events appear in order:

    fetch.start → primary.complete → fallback.decision → sidecar.start
    → sidecar.complete → fetch.complete

For each event the runtime / CF-signal / decision fields are the first
keys after `event`, so a verification grep does NOT need to walk into
nested structures to confirm the sequence. The same flag manipulates
both the threshold and the contract so future ACs can keep adding events
without touching the CLI surface.
