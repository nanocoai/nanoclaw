================================================================================
Why a deterministic harness, not a live LLM agent run
================================================================================
The SKILL.md workflow has six sections:

  0. legacy state migration (deterministic, run-once)
  1. state load + setdefault for AC-2 keys (deterministic)
  2. source-by-source polling — Source C (pap) is the migration target
  3. LLM classification (non-deterministic, sends Discord alerts)
  4. map rebuild (deterministic, only when ≥1 listing passes classify)
  5. state commit (deterministic)
  6. pap failure-alert check (deterministic)

The migration touches Sections 0/1/2C/5/6 — all of which are deterministic
bash/python steps that the LLM agent invokes verbatim. To prove the cron
cycle survives end-to-end without (a) consuming Anthropic API credits, (b)
sending a real Discord alert to dc:1485303434541273220, or (c) mutating
production state, we drove the deterministic spine via a faithful
translation of the SKILL.md instructions and stubbed Section 3 to mark
every candidate as `reject` — the SAME branch the real skill takes for
listings outside the buyer's box. Sections 4 (map rebuild) and 5 (commit)
then run with the stub-mutated `seen` set, exactly as in production.

The harness file is `/tmp/cron-sim-2c/cron_sim.py`, a one-to-one
restatement of SKILL.md Sections 0/1/2C/4/5/6. It runs against a temp
copy of the real state file so production `~/webdav-data/.paris-rental-seen.json`
is never touched.

Notes for AC 5 (image rebuild) and the parallel siblings
================================================================================
- The bind-mount of /opt/web-fetch/* is an artifact of the still-blocked
  image rebuild called out in AC 1's evidence; once the rebuild lands the
  cron sim can drop the four `-v …web-fetch/*.py:/opt/web-fetch/*.py:ro`
  flags and run against the baked image alone. The python harness itself
  is unaffected.
- The AC 2-B sibling task removes host-helpers/paris-pap-fetch/, the
  com.nanoclaw.paris-pap-fetch launchd plist, and the staging/failure
  JSONL files. This cron-sim run already exercises the post-2-B world:
  no SKILL.md instruction reads from those paths, and the harness does
  not touch them. After 2-B lands, the only change to this AC is that
  the host-side helpers are gone — the run command above is unchanged.
- The AC 2-D sibling task tunes the failure-alert threshold semantics
  inside Section 6 (silent log on single failure, alert only on
  PAP_FAILURE_THRESHOLD≥3 consecutive). The cron sim already exercises
  the success path (consec=0 → would_alert=false) and is ready to
  exercise the failure path by toggling `pap_consec_failures=3` in the
  temp state and re-running — this is documented but out of scope here.
- The harness lives at `scripts/paris-rental/cron_sim_2c.py` (alongside
  the other paris-rental verification scripts) and is reusable: pass a
  state file path via /workspace/sim and it will replay Sections 0, 1,
  2C, 4 (skipped when no listing passes), 5, and 6 against any state
  snapshot. Section 3 (LLM classify) is replaced by a deterministic
  `reject` stub so the post-classify branches (seen.add, state.commit)
  stay exercised without consuming Anthropic API credits.
- Companion run log: `scripts/paris-rental/cron_sim_2c.run.log` —
  preserves the abridged trail above (32 page fetches, 470 cards, 28
  candidates, 0 errors, exit_code=0).
