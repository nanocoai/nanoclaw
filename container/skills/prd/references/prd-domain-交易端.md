# 交易域 PRD 参考（prd-domain-交易端）

> 交易域特有规则。通用写作规律见 prd-core.md,工序流程见 prd-pipeline.md。

## 域定位

> 交易端 = **有前端页面**（前台交互 / 字段 / 展示规则 / 状态驱动）的交易业务需求。本文件规律出自 323 篇线上交易 PRD 反推，均带真实 PRD 锚点（六位编号，如 `PRD-368610`）——锚点是**判断规则**不是可照抄的成品，别把锚点原文整段搬进你的 PRD。

## 域章节清单

### A 类 — 必写章节（标题 + 实质内容，6 个）

落档的 PRD 正文中**必须出现**以下章节标题和实质内容。LLM 自我审视：A 类章节标题写齐了吗？schema 详见下方章节实操指南各章节段，**A 类直接抄结构填值**。

| 章节 | 内容要求 |
|------|---------|
| **头部 · 协作部门/负责人表** | 2 列 5 行表（schema 见下方 ### 头部段）|
| **版本变更表** | 4 列表（版本/时间/变更人/内容）|
| **一、需求背景** | 段落 + 数据现状（不能只写"用户体验差"）|
| **二、需求价值** | 定性或定量论证（不能只写"提升体验"）|

### B 类 — 按条件必写（标题 + 引导提醒，2 个）

## 交易签名手法

- **状态×条件 → 展示态 + toast 矩阵（三态穷举）**：前台按钮/入口把「展示 / 置灰 / 不展示」三态按维度穷举进矩阵，每格写死展示态 + 对应 toast 文案。锚点 `PRD-339734`（取消/退货按钮＝订单服务×类型×阶段，每格给展示态+toast）、`PRD-342330`（三因子真值表 6 行）。
- **前台成品文案写死成上线原文 + 边界降级穷举**：toast/按钮/气泡/短信文案一字落地，变量用 `{var}` 单花括号占位（禁 `${`,落档通道会解析成公式），并写清取不到值时的兜底。锚点 `PRD-351863`（`${Name}${行情涨X%}` + 「取不到价格整句删」）、`PRD-342276`（未成年错 1~5 次每个 toast 原文全给）。反例 `PRD-329494`（甩「详见设计稿」只贴图，前端无法落地）。
- **grid 左图右文承载原型**：改前改后 / 竞品对比用 grid 左右并排，别上下堆图；每个 UI 元素给「取值 / 交互 / 文案」三元组。锚点 `PRD-367385`（改前后原型并置）、`PRD-359823`。
- **单元格底色做状态展示态语义编码**：绿=正常展示 / 灰=置灰 / 无色=不展示 / 黄=本次新增列，把高维展示矩阵压成扫一眼颜色即懂。**此为局部图例,与全局色板语义不同——用此编码的表格,表首必须一句局部图例声明,声明后节内局部优先**。锚点 `PRD-339734`。（S4 写作时先写显式文字，并直接在 `<td background-color>` 上色，用 `light-green`/`light-gray`/`light-yellow` 等淡色——单元格底色是块级属性归写作侧；S9 只管行内）

## 内容→结构决策表

核心 = **结构服务判断**。本该矩阵却压平成单层列表、本该状态机却堆嵌套列表、本该拆多行却塞进一个表格单元——都是失败；反过来，小需求硬塞表格和多层嵌套 = 过度结构化，也是 AI 味。下表正/反例只给 PRD 号 + 一句话判断，回查原文自行取证。

| 看到 X 内容 | 用 Y 结构 | 正例 / 反例（锚点） |
|---|---|---|
| 多维/多状态/多场景组合枚举 | 矩阵表格（维度作行列，格填展示态+toast/阈值/✅❌），绝不压平成单层列表 | 正 `PRD-339734`/`PRD-342330`/`PRD-326172`；反 `PRD-367424`（压成单层列表，父子靠缩进想象）|
| 状态流转 / 多层判断分支 | 状态机 / 流程图 / ASCII 决策树（图类型表见 prd-core.md 6.1 段），绝不堆多层嵌套有序列表 | 正 `PRD-352044`/`PRD-348827`；反 `PRD-366997`（平铺列表，作者自己都建议加状态机表）|
| 改前改后 / 现状 vs 本期 | 并列多列对照表让 delta 自解释；含原型则 grid 分栏 | 正 `PRD-364124`（四列对照）/`PRD-326702` |
| 接口 / 字段 / 枚举 / 取数口径 | 字段表逐行（字段｜类型｜必填｜枚举｜示例，增量标新增/已有）或代码块贴 struct/enum/SQL | 正 `PRD-367990`/`PRD-348295`；反 `PRD-351827`（11 列过宽横滑，应转置）|
| 抽象规则 / 计算公式 | 规则后紧跟代入真实数字的算例；纯公式放代码块 | 正 `PRD-348417`/`PRD-315267` |
| 背景 / 痛点 / 数据现状 | 分层 bullet / callout，每条加粗 headline + 因果 + 硬数字 | 正 `PRD-326172`/`PRD-332894`；反 `PRD-333430`（分号串成 200 字 run-on）|
| 需求本质 / 概述 | callout（📌）一句话前置（从 X 升级为 Y）再展开——核心结论用 callout 钉住，别放引用容器（那是旁注层，读者会跳过） | 正 `PRD-368610`/`PRD-354820`；反 `PRD-345303`（全平铺读不出主次）|
| 长文档 / 多子需求 | 开头需求清单表当目录（序号｜需求｜章节｜优先级）；合并型加来源表 | 正 `PRD-348827`/`PRD-351240`；反 `PRD-360895`（60 条塞单格深层嵌套）|
| 多渠道触达 / 消息 | 宽表一行一条完整配置（场景/触发/频率/各渠道文案/模板code/跳转/频控），文案 `{变量}`+降级 | 正 `PRD-336778`/`PRD-351863` |
| 重复出现的口径/样式/策略 | 单一真源表 + 按名引用（DRY），改一处全端生效 | 正 `PRD-360264`（时效主表，各页只引用）；反 `PRD-328354`（三页逐字复制）|
| 范围边界 / descope | 「本期不做/不包含」表列条目 + 原因（详见 §「五章范围写法」）| 正 `PRD-364455`/`PRD-357700` |
| 单点结论 / 轻量小需求 | 保持一句话 + 段落，别硬塞表格/多层嵌套（详见 §「按 PRD 类型套骨架」·F）| 正 `PRD-367654`/`PRD-339756`；反 `PRD-358139`（简单能力撑成十章+空章节）|

> 做表护栏：语料表格率 86%，但"该做矩阵就做矩阵"与"该用一句话就别做表"要成对用；无脑做表 = 万物皆表 = 过度结构化的 AI 味。

## 按 PRD 类型套骨架

下面每类只列「必须有 + 常见坑」，都在 §「域章节清单」10 章框架内按体量裁剪，不是另起一套章节。

- **A 版本补充/变更型**：变更记录表（版本｜时间｜变更人｜摘要｜位置）+ 文首声明颜色图例 + 正文改动刷**分色底色**定位（V2黄/V3绿/V4蓝）+ 显式标 新增/不变/复用。坑：**版本 diff 用分色底色+变更表，不用删除线堆版本对比章节**。删除线两个合法用法（`PRD-351240`/`PRD-333149`/`PRD-363619`）：整块划掉=descope/内容作废留痕（主用法，语料 93.6%）；句内划旧值+旁写新值=单点口径变更留痕（如 划"必填"留"非必填"）——仅限零星单点，不得用于系统性版本对比章节。
- **B 实验型**：结论钉文首（成没成/推不推全+关键指标）+ go/no-go 决策规则（推全/迭代/关停三条件）+ 假设写明相关≠因果+灰度 + 核心指标 **+ 护栏负向指标**。坑：只报正向指标无护栏 = AI 味（`PRD-361156`/`PRD-365583`）。
- **C 前台展示规则型（签名最密集）**：一句话描述前置 + 状态×条件→展示态+toast 矩阵（三态穷举）+ 成品文案写死+边界降级 + grid 左图右文原型 + 底色语义编码。坑：甩「详见设计稿」只贴图前端无法落地（`PRD-339734`/`PRD-345307`）。
- **D 接口/后台改造型**：一句话需求 + 需求清单表 + 字段表 + struct/enum/SQL 代码块固化口径 + 时间窗口径精确 + 验收 Given/When/Then（命中/未命中/异常）**+ unhappy-path 超时阈值+降级+日志**。坑：字段做成过宽横表需横滑→转置（`PRD-362854`/`PRD-367990`）。
- **E 数据/算法/看板型**：口径参数化成表（指标｜口径｜取数SQL｜时间窗）定义一次 + 行列维度先声明再填 + 阈值抽象成命名可调参数（`PRD-354939`：m=4/a=20 标可配置）。坑：逐入口/逐字段复制口径、60 条塞单格（`PRD-354553`/`PRD-360895`）。
- **F 轻量 bugfix/小需求型（反向护栏）**：极简两段「问题表现 / 解决方法」各一句；接口类只写 入参→出参+数据源+一张截图。坑：简单能力撑成十章 + 「八章 无」空占位 + cursor 交互残留（`PRD-367654`/`PRD-339756`，反例 `PRD-358139`）。

### 一、需求背景

飞书 PMO 三段，按需挑：

- **产品/数据现状**：沿用用户/飞书原文；用户明示要补才用代码验证补全
- **用户调研**：LLM 不编造，无素材直接跳过
- **竞品分析**：可指出友商已有公开同类功能（事实陈述）；不编造转化率/MAU/营收等具体数据

### 二、需求价值（A 类必写）

论证「为什么值得做」，定性或定量，**不能只写"提升体验"**：

- **业务价值**：解决什么业务痛点、带来什么结果（如：减少客服工单、提升转化、降低差评/退款）。有数据就引数据（沿用用户/飞书原文，不编造）；无数据就定性说清受益方与受益点。
- **用户价值**：目标用户是谁、他们原来卡在哪、改完后体验怎么变。
- **不达标反例**：❌"提升用户体验" / "优化流程" —— 空泛无对象无结果，等于没写。

### 三、需求概述（C 类）

仅在多模块交互依赖时写，单一功能点可跳过。围绕几个核心关键点说明产品方案设计思路。

五、需求范围 — **必用 3 列表**（同一域前缀连续 ≥3 行 → 拆"域"独立首列成 4 列,不逐行重复）：

| 模块 | 改动点 | 负责人 |
|------|--------|--------|
| [业务域 · 后台模块] | [具体改动，如：新增规则档位/配置项] | 后端 + 前端 |
| [业务域 · 服务/接口] | [改动，如：增加字段透传] | 后端 |
| App 端 · [页面名] | [展示/交互改动] | iOS + Android |

❌ 「优化 95 分回收业务 | 不确定」
   ←「优化」太模糊，"不确定"是空头

**「明确不包含」**：每份 PRD 建议至少 2 条明确排除项，防止范围蔓延。放在五章末尾（或三章末尾）：

```

- iOS 端售后流程改动（独立需求 D 处理）
- 历史数据回溯（已发布商品标签不刷新）
```

「本期范围外」单独列行（不是省略）。

## 6.3 功能主体与质量标准

**何时用 5 列表 vs 段落**：
- ✅ 跨 2+ 模块 或 改动点 ≥ 2 → 必用 5 列表（让 PM/RD/UX 能按行对照）
- ❌ 单模块单改动点 → 段落足够，不强求列表
- ⚠️ 含截图/原型时必用 5 列表（截图直接嵌"交互图"列单元格,禁止表外堆图）

| 域 | 模块 | 功能 | 功能详细说明 | 交互图 |
|------|------|------|------------|--------|
| [业务域] | [功能模块] | [功能点简称] | 用户进入 [页面] → [操作] 展示 [选项/结果]。[服务]接口异常时降级展示「[兜底文案]」。| [该场景截图进本格] |
| App 端 | [页面名] | [功能点简称] | 加载 [数据] 后，[区域] 根据 [关键字段] 展示 [结果]。无 [字段] 时不展示。| [截图] |

**域列与归并**：同一域前缀连续 ≥3 行 → 域独立成列不逐行重复（本表即该形态;同域行也可用 rowspan 竖向合并,落档通道已实测支持）。行间引用按模块名（「文案规则同"出售首页"」）,不设序号列。

**每条功能说明的质量标准**：

- 触发条件 + 处理逻辑 + 返回结果 三段齐全
- 边界 / 异常在同一行描述（"调用 X 失败时降级展示 Y"），不另起一行
- 涉及状态机：列出全部合法状态 + 流转条件（含禁止流转，如"已发货后不可取消，必须走退款"，不能只写部分）

⚠️ 反例 — 别拆成 `####` + bullet（chat 5096dddd 最严重错误）：

```
❌ #### 4.2.2 [业务后台]
   - **[功能模块 A]**：[新增/修改功能描述]
   - **[功能模块 B]**：[新增/修改功能描述]

❌ #### 4.2.3 App 端
   - **[页面 A]**：[展示/交互改动]
   - **[页面 B]**：[展示/交互改动]
```

## 条件章节

### 6.4 历史数据处理（D 类）

仅在涉及存量数据影响时写（字段迁移 / 状态重算 / 兼容旧版本）。明确处理方案，避免造成事故。偏后端的产品方案常需要。

### 七、埋点（B 类）

触发条件：需求涉及「前端」或「移动端」→ 写；纯「后端」/ 纯内部工具 → 省。

**引导模板**：

> 埋点参数涉及 NINE 内部规范，建议跟数据团队对齐后补全。
> 常见维度：当前页 id / 模块 / 触发动作 / 上下文参数 / 新增 or 调整。

### 八、非功能（B 类）

触发条件：research 中发现实质问题（客服话术 / 法务合规 / 运营预案 / 灰度方案 任一）→ 写实质内容；无发现 → 省。

**引导模板**：

> 实质内容按 research 发现类型分块（按需选取）：
> - **客服预案**：新功能上线后的用户咨询话术 + 客服权限配置
> - **法务 / 商务签约**：涉及合规、外部合作时的签约状态
> - **运营配合**：活动配置、内容审核规则
> - **灰度方案**：分批上线的范围、节奏、回滚条件

### 九、项目规划（D 类）

大型项目（多模块、多团队、有里程碑）需要项目规划推进表，明确不在需求内的其他人员需要做的内容。小项目可跳过。可使用甘特图表示。
