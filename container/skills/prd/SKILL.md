# 共识型 PRD 生成

把用户和 LLM 的对话整理成一份人类能看懂、能确认方向、能继续转 OpenSpec 的需求文档。目标不是写长，而是消除歧义、形成共识。

这个 skill 的角色不是"模板填空器"，而是**主动共识教练**：信息不够时，先给出自己的理解、建议方案和缺口判断，再用少量关键问题推动用户确认。

## 为什么要固化（这个 skill 的设计逻辑）

PRD 每次跑出来不一致，根因是 **AI 有太多临场决策自由**：写哪些章节、写多详细、要不要画图、什么算写完，全靠当场发挥。本 skill 用四个机制把这些决策点前置成硬规则，让 AI 只执行、不临场判断：

1. **先判类型，再套固定骨架** —— 四类需求各有写死的章节顺序，不许增删。
2. **每节挂必答清单** —— 该节必须回答的问题写死，答不全不许进下一步。
3. **正例 + 反例锚定质量** —— 给"合格长这样"和"这样判不合格"，不靠 AI 自己理解。
4. **输出前强制自检 gate** —— 用必答清单逐条勾，缺项必须显式声明，禁止瞎编凑格式或偷偷跳过。

漂移来自决策自由，把决策变成规则和必答题，稳定性就出来了。

## 核心原则

1. **先讲人话，再讲系统**：第一屏让没参与讨论的人也能看懂背景、问题和目标。
2. **区分事实、推断、待确认**：用户明确说的、代码/日志证据、模型推断、还没确认的事必须分开标注。
3. **方案要能被质疑**：写清为什么这么做、风险在哪、哪些替代方案暂不选。
4. **必须能转 OpenSpec**：PRD 是人类共识层，OpenSpec 是机器执行层；验收标准要能变成 scenarios。
5. **以终为始**：先明确最终效果，再倒推验收标准、E2E 用例、实现方向。
6. **主动给建议**：信息不足时先写"我建议的默认口径"，再让用户确认或修正，不空等。

## 禁止事项

- 禁止直接写代码、改文件、提 PR、部署。
- 禁止 PRD 未确认就生成 OpenSpec、建议开始实现、提 PR、部署或跑 E2E。
- 禁止把未确认的推断写成事实。
- 禁止使用"大概"、"可能"、"体验更好"、"更流畅"这类没法验收的表达；必须改成可判断的条件。
- 禁止只复述用户原话，要做结构化提炼。
- 禁止删掉骨架里的章节；本次无内容的章节必须保留并写"本节不适用 + 原因"。
- 禁止把答不全必答清单的草稿伪装成"确认候选版"。

## 工作流总览

```
Step 1 判类型 → Step 2 定输出形式 → Step 3 主动补齐信息
       → Step 4 按类型骨架生成 PRD（含画图） → Step 5 自检 gate + 自评分 → Step 6 落账本
```

## Step 1：判需求类型（先判后写）

每份 PRD 开头必须先声明类型。骨架只有**两套**：Bug 走专用模板，其他全走标准模板。

| 类型 | 特征 | 用哪套骨架 | 重心 |
|------|------|-----------|------|
| **Bug 修复** | 修一个具体故障、错误行为、异常现象 | **模板一（Bug 专用）** | 复现 + 问题定位 + 根因证据链 |
| **新功能** | 新增一个用户能感知的能力 | **模板二（标准）** | 用户与场景 |
| **重构 / 技术债** | 改内部实现，对外行为基本不变 | **模板二（标准）** | 兼容与迁移 + 前后对比 |
| **系统能力 / 平台级** | 新产品能力、复杂角色、跨系统链路 | **模板二（标准）** | 方案思路里的架构与跨系统图 |

判定规则：

- 有明确"坏了/报错/不对"现象 → Bug 修复（模板一）。
- 其余一律走标准模板（模板二），类型只决定**哪几节加重**，不改骨架。
- 拿不准时按标准模板处理。

声明格式：`> 类型：新功能（标准模板）| 状态：草稿版`

## Step 2：确定输出形式

### 铁律：图文一体，单一文档

**一份 PRD 就是一个完整文档，图 inline 嵌在对应章节正文里，文字和图浑然天成。**

- **禁止图文分离**：禁止把正文放一个文件、图放另一个文件（如单独的 `diagrams/` 目录）再用链接互指。读者打开文档就看到该看的图，图就在它解释的那段文字旁边。
- **唯一交付物 = 图文一体文档**：最终交付是**一个**自包含文档，所有图嵌在正文对应章节中。生成图的单独 HTML/PNG 只是过程临时件，不作为交付物给用户。
- **主载体必须是飞书文档（docx）**：这是用户最高优先级偏好，不许用 HTML 文件、云盘附件、Markdown 顶替。HTML 只在 feishu-docs 不可用时降级。

### 飞书文档图文一体的标准做法

用 `feishu-docs` 把正文和图按章节顺序**交替写入同一个飞书 docx**，图就落在它解释的那段文字后面：

1. 三张 SVG（diagram-design 生成）先用 Chrome headless 渲染成 PNG（`--force-device-scale-factor=2` 高清）。
2. `feishu-docs create "标题"`（stdin 传第 1 段正文，到第一张图之前）→ 拿 document_id。
3. `feishu-docs insert-image <doc> arch.png --caption "图 1 ..."` 插架构图。
4. `feishu-docs append <doc>`（stdin 传下一段正文）→ `insert-image` 插下一张图 → 交替直到写完。
5. append 与 insert-image 都追加到文档末尾，**只要按章节顺序调用，图就落在正确位置**。
6. 最后 `feishu-docs read <doc>` 验证图都插进去了（grep image block + 章节标题对位），别让用户当测试员。

默认保存策略：

- 交付物：飞书文档（docx），正文 + 图按章节交替写入，URL 写回任务账本和发给用户。
- 账本底稿：同步存一份 Markdown 到 `groups/global/task-ledger/<task-id>/prd.md`（底稿可用 Mermaid 占位）。
- 中间产物：图的 SVG/PNG、可选的图文一体 HTML 放 `task-ledger/<task-id>/`，不当交付物。

降级说明（环境没暴露对应工具时必须标注）：

- `feishu-docs` 不可用 → 退而求其次出图文一体 HTML 本地文件，**明确标注"飞书文档待补"**，不能假装 HTML 就是交付物。
- `diagram-design` 不可用 → 正文内用 Mermaid 占位，标记"复杂图件待替换"。

## Step 3：主动补齐关键信息

缺信息时不要硬编，也不要只甩问题给用户。按这个顺序输出：

1. **我现在的理解**：3-6 句复述问题和目标。
2. **我建议的默认口径**：给出你认为合理的目标效果、非目标、验收方向。
3. **缺口判断**：哪些信息不够、为什么会影响后续实现。
4. **关键追问**：只问 1-3 个最能推进共识的问题。

```markdown
## 我建议先按这个方向理解
...

## 现在还差 2 个确认
1. ...
2. ...
```

## Step 4：按类型生成 PRD

每类的章节骨架**写死，顺序固定，不许增删**。每节下方的"必答清单"是该节必须回答的问题，答不全该节不算完成。

### 画图硬规则（业务文案版皮肤 + 粒度分层）

PRD 和图是一个整体，写 PRD 时同步画，不是事后补。

**PRD 的图默认用「业务文案版皮肤」**——受众是业务方/管理层/产品，目的是对齐共识，讲"业务上发生了什么、谁做了什么、有什么价值"，不是"代码怎么实现"。皮肤规则见下方 §图的语言层级。**只有给研发看的章节（如「方案思路 / 系统边界」）才切到工程术语版皮肤。**

> ⚠️ 这跟早期"统一用偏工程的 PlantUML"是相反的——PRD 默认不画工程实现图，那是 `tech-doc` skill 的事。

工具仍统一用 **PlantUML**（业务版同样用 activity / sequence 画，只是节点文案、泳道、异常分支按业务版规则裁剪）；要像素级精控才回退 `diagram-design` 手画 SVG。

---

#### 图的语言层级（双皮肤 · 与 tech-doc 对称，改一处须同步另一处）

同一套流程逻辑，按受众切两种皮肤，**一份逻辑两种画法**：

| | **业务文案版（PRD 默认）** | **工程术语版（tech-doc 默认）** |
|---|---|---|
| 受众 | 业务方 / 管理层 / 产品 | 研发 / onboarding |
| 泳道 | 只分**业务角色**（如 招聘专员 / AI助手），不出现系统名、模块名 | 真实系统 / 模块（MainAgent / recruit-api / CDP） |
| 动作措辞 | 全程人话 + 拟人（"像真人一样翻看""读简历判断是否合适"） | 真实函数 / 接口 / 锁 / 回调 / 状态机名 |
| 异常分支 | 只留**业务关心的**（如"需要扫码登录"）；busy / 锁 / 超时 / 重试**全藏掉** | 异常出口全画（busy / need_login / need_verify / timeout） |
| 术语 | 翻译成业务话：`sourcing_resume_poll`→"继续找下一批"、`seen-set 去重`→"不重复联系同一人" | 保留技术原名，可标代码文件 / 行 |
| 收尾 | 底部标**价值点**（为什么比人工强：7×24、不漏人、断了能续） | 标代码出处 / 约束 / 边界 |
| 张数 | **精**：1-2 张端到端主线即可，不要一接口一张 | 按粒度分层可多张 |

**业务版自检 6 条**（PRD 主线图逐条过）：① 泳道只有业务角色？② 有没有混进函数名 / 模块名 / 技术黑话没翻译？③ 技术异常藏干净了吗？④ 动作是不是人话 + 拟人？⑤ 底部有价值点吗？⑥ 张数是否克制（≤2 张主线）？任一不过就重画。

> 工程术语版的完整规则在 `tech-doc` skill；本表是两个 skill 的**共享契约**，任何一边改了表，另一边同步改。

---

命中以下任一条件**必须画图**，不靠 AI 临场判断：

| 命中条件 | PlantUML 图类型 |
|---------|----------------|
| 跨系统调用 / 消息往返 | `sequence` 时序图 |
| 4 步以上状态流转 / 暂停恢复 | `state` 状态机 |
| 模块 / 组件 / 部署关系 | `component` 或 C4 架构图 |
| 决策分支流程 | `activity` 流程图 |
| 数据模型 / 实体关系 | `class` / `entity` |

**渲染命令**（中文正常）：`java -jar /tmp/plantuml.jar -tpng x.puml -o <dir>`（加 `skinparam dpi 150` 提清晰度）。注意：`state` / `component` / `class` 图需系统装 `graphviz`（`dot`），`sequence` / `activity` 不需要。环境无 jar / dot 时降级 kroki.io / 在线 server，并标注"图待渲染"。

**粒度分层（铁律）**：一张图只服务一个层级——流程级 / 交互级 / 协议级。需要更细时，把目标框**展开成下一张完整图**，严禁在单图里硬塞多层级细节。宁可两张清晰的分层图，不要一张啥都有的糊图。

**嵌入规则**：图必须 inline 在它解释的那段章节正文里（时序图在"方案思路/链路"节、状态机在状态相关节、架构图在架构节）。飞书文档用 `feishu-docs create` + `insert-image` 按章节顺序交替写入，PNG 落在对应正文后。禁止堆文末、禁止图文分离成两文件。

各模板对图的最低要求：Bug 模板按需（涉及流程/时序才画）；标准模板至少一张能体现核心机制的 PlantUML 图；系统能力类必须架构图 + 至少一张时序/状态图，且按粒度分层拆成多张，全部 inline。

### 模板一：Bug 修复（专用，以复现和定位为主）

```markdown
> 类型：Bug 修复 | 状态：{探索中/草稿版/确认候选版/已确认}

# {故障名}
> 一句话定位：{什么场景下、什么操作、出现什么错误现象}

## 1. 背景
## 2. 复现路径
## 3. 问题定位与根因
## 4. 修复方案
## 5. 非目标
## 6. 风险与待确认
## 7. 验收标准
## 8. 回归 / E2E 用例
```

必答清单：

- **标题 / 一句话定位**：故障名 + 一句话说清场景、操作、现象。
- **1 背景**：什么场景下、什么操作、出现什么错误现象？影响哪些用户 / 多大范围 / 从什么时候开始？（纯描述现状）
- **2 复现路径**：能不能稳定复现？前置 / 操作 / 现象三件套。不能复现要写"暂不可复现 + 已知触发条件"。
- **3 问题定位与根因**：已确认事实（引用日志行 / 代码行 / commit）；模型推断；待确认。**禁止无证据猜根因。**
- **4 修复方案**：改什么行为、影响哪些路径，偏系统行为语言；涉及流程变化补 PlantUML 时序/流程图。
- **5 非目标**：这次明确不顺手改什么。
- **6 风险与待确认**：修复可能引入的副作用；需要用户拍板的点。
- **7 验收标准**：可被测试人员直接验证（至少含"原现象不再出现"+"没引入新问题"两条）。
- **8 回归 / E2E 用例**：至少 1 条，含前置条件 / 操作路径 / 预期结果 / 证明的效果。

正例（根因节）：
> 已确认事实：`bot.py:1477` 把 DB 残留值 `claude_loop` 映射到 `nine_loop`，但 2026-05-15 PR#2067 漏写 ALTER 进 run_migrations()（`main.py:1098` 复盘注释），导致线上 group_config 缺列、main_agent 写库报错。证据：GlitchTip 异常 #4821 + Loki 日志 `column not found`。

反例（判不合格）：
> "应该是配置没生效导致的，可能是缓存问题，改一下就好了。" —— 无证据、无日志、无代码定位，纯推断，禁止。

### 模板二：标准模板（新功能 / 重构 / 系统能力 通用）

顶层分**两大块**：【是什么】只讲背景现状；【要什么】从目标往下排。标题朴实，不用"战略定位"这类花哨名。

```markdown
> 类型：{新功能 / 重构 / 系统能力} | 状态：{...}

# {需求名}
> 一句话定位：{用一句话说清做什么、给谁、解决什么}

<!-- 【是什么】描述层 -->
## 1. 背景

<!-- 【要什么】需求层 -->
## 2. 目标
## 3. 非目标
## 4. 用户与场景
## 5. 方案思路
## 6. 兼容与迁移
## 7. 风险与待确认
## 8. 验收标准
## 9. E2E 用例
## 10. （附）可转 OpenSpec
```

必答清单：

- **标题 / 一句话定位**：必须有需求名 + 一句话定位，让人一眼知道做什么、给谁、解决什么。
- **1 背景**（是什么）：现状、痛点、为什么现在做。**纯描述，不掺方案和诉求**，让没参与的人看懂当前世界长啥样。
- **2 目标**（要什么起点）：做到什么算成功？用**可量化指标**衡量；给用户/业务什么价值。
- **3 非目标**：这次明确不做什么，防范围蔓延；涉及线上老流程的写明"绝不碰"。
- **4 用户与场景**：谁用？主场景 / 异常场景 / 边界条件。
- **5 方案思路**：流程、关键交互、系统边界。**按需画 PlantUML 图并遵循粒度分层**（一图一层级，要细就拆图）。
- **6 兼容与迁移**：影响老用户 / 老数据吗？灰度、双轨、回滚策略。
- **7 风险与待确认**：已确认事实 / 模型推断 / 风险 / 待用户拍板，分开标。
- **8 验收标准**：主流程 / 异常 / 边界各至少一条可验证条件。
- **9 E2E 用例**：至少 1 条完整端到端路径（系统能力类至少 2 条）。
- **10（附）可转 OpenSpec**：Capability / Requirement / Scenario 初步映射。

#### 按类型加重（同一骨架，不同侧重）

| 类型 | 重点加重的节 | 必画的图 |
|------|-------------|---------|
| **新功能** | 4 用户与场景、8 验收 | 5 节主流程图（activity / sequence） |
| **重构** | 6 兼容与迁移、8 验收（行为不变性） | 5 节放**改造前后对比图**；声明对外行为不变 |
| **系统能力** | 5 方案思路（架构 + 跨系统）、4 角色 | 5 节架构图（component/C4）+ 时序图，按粒度分层拆多张 |

正例（目标节）：
> 核心目标：把 ask_choice 封闭选择从纯文本改为飞书表单卡片。成功指标：封闭选择场景卡片渲染率 100%（当前 0），用户点选后回填正确率 100%。用户价值：减少手输歧义，选项一目了然。

反例（目标节，判不合格）：
> "目标是让选择体验更好、更流畅，提升用户满意度。" —— "更好/更流畅"无法验收，无量化指标，禁止。

正例（方案思路节，重构）：
> 动：`tools/recruit/sourcing_v2/` 新建连接层。不动：`tools/recruit/*` 老流程（线上在跑，diff 禁止出现）。对外行为不变，双轨并行。附改造前后对比图。

反例（方案思路节，判不合格）：
> "把招聘流程整体重写一版，更清晰。" —— 未声明行为不变性、未划绝不碰范围、无图，禁止。

## Step 5：自检 gate + 自评分

输出 PRD 前**必须**先跑自检 gate，再自评分。两关都过才能标"确认候选版"。

### 自检 gate（逐条勾必答清单）

按当前类型的必答清单**逐条勾**。每节标 ✅ 已答 / ⚠️ 缺信息已声明 / ❌ 漏答。出现 ❌ 必须回去补，不许往下走。⚠️ 必须在 PRD 对应章节显式写"本项缺 XX 信息，需用户确认"，禁止瞎编填上。

除必答清单外，gate 还**强制**检查图文一体三项（任一不过则 gate 不通过）：

- **图都画了吗**：命中画图硬规则的图是否都生成，且**用 PlantUML 渲染成 PNG**（Mermaid 占位顶替交付图 = ❌）？
- **皮肤对了吗**：主线图是不是**业务文案版**（过 §图的语言层级 的业务版自检 6 条）？混进函数名/模块名/未翻译技术黑话、技术异常没藏 = ❌。给研发看的章节用工程版可放行。
- **粒度分层了吗**：是否一图一层级？有没有单图硬塞多层级细节该拆没拆（= ❌）？
- **图 inline 了吗**：图是否嵌在它解释的章节正文旁，而不是堆文末或放在另一个文件？
- **图文分离了吗**：交付物是不是**一个飞书文档**？若正文和图还是两个文件、或主载体不是飞书文档 = ❌。

```markdown
## 自检 gate（标准模板·系统能力）
- 1 背景：✅
- 2 目标：⚠️ 缺量化指标，已在正文标注待确认
- ...
图文一体检查：
  - 图都画了（PlantUML 渲染 PNG）：✅
  - 粒度分层（一图一层级）：✅
  - 图 inline 嵌在对应章节：✅
  - 交付物是单一飞书文档：✅
gate 结论：通过 / 不通过（有 ❌）
```

### 自评分（100 分）

- **可读性 20**：没参与讨论的人 3 分钟能否看懂。
- **共识度 20**：目标、非目标、边界、待确认是否清楚。
- **根因/痛点清晰度 20**：A/C 类看证据链，B/D 类看痛点链。
- **方案完整度 20**：主流程、异常、兼容、风险、图件是否到位。
- **可验证性 20**：验收标准和 E2E 用例能否证明目标效果。

```markdown
## PRD 自评
总分：{N}/100
- 可读性：{N}/20，理由：
- 共识度：{N}/20，理由：
- 根因/痛点清晰度：{N}/20，理由：
- 方案完整度：{N}/20，理由：
- 可验证性：{N}/20，理由：

PRD 状态：探索中 / 草稿版 / 确认候选版 / 已确认

## 需要用户确认
1. ...
```

状态与动作规则：

- **gate 有 ❌ 或自评 < 70**：只输出理解、建议方向、追问，不输出完整 PRD。
- **gate 通过且 70-84**：输出草稿版，明确缺口，不进入下一步。
- **gate 通过且 ≥ 85**：输出确认候选版，询问用户是否确认。
- **已确认**：只能由用户明确说"确认/可以/就按这个/开始实现"触发，AI 不能自封。

低于确认候选版，不允许进入 OpenSpec 或实现。

## Step 6：与任务账本 MCP 的关系

环境提供任务账本 MCP 时：

- 生成草稿版后：创建 / 更新任务，状态 `prd_draft`，写入飞书文档 URL、Markdown 路径、图件路径。
- 用户确认后：状态推进到 `prd_confirmed`。
- PRD 未确认前：不得调用实现、E2E、ship 类流程。

MCP 不可用时：继续生成 PRD，但在回复里说明"未落账本"。

## 完成标准

一份合格 PRD 必须让用户看完能回答：为什么做？这次做什么？这次不做什么？有哪些不确定？怎么判断做对了？下一步能不能转 OpenSpec？答不出就继续追问或重写，不进入后续实现。
